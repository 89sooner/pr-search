# 리스크 · 불확실한 가정 · 함정

## 절차 함정 (이 세션에서 실제로 밟은 것들)

### 1. 등가 변이를 킬로 착각하지 마라 — 두 WP 연속으로 나왔다

- **WP-026 M3**: "직전 대비 PR 수"에 `count(DISTINCT pull_request_number)`와
  `WHERE pull_request_number IS NOT NULL`이 **함께** 있어, 각각을 지우는 변이가
  **둘 다 살아남았다** (`count(DISTINCT col)`은 NULL을 세지 않는다). 둘을 함께
  지운 변이가 `expected 3 to be 2`로 킬됐다.
- **WP-027 M3**: `if (next && phase === 'idle') load()`에서 `next &&`만 떼는
  변이가 살아남았다 — 접는 시점에는 이미 조회가 끝나 `idle`이 아니다. **마운트
  조회**로 바꾸자 여섯 시험이 잡았다.

→ 변이를 걸었으면 **답이 실제로 달라지는지** 먼저 확인한다. 살아남았을 때
"시험 구멍"이라고 결론 내리기 전에 "등가 변이인가"를 의심한다.

### 2. lint는 마지막 파일을 쓴 뒤에 다시 돌려라

WP-027 백엔드에서 라우트 등록 직후 `pnpm lint`를 돌리고 **통합 시험 파일은 그
뒤에 썼다.** 그래서 커밋 메시지의 "lint 통과"가 그 파일을 본 적 없는 결과였고,
미사용 import(`vi`)가 커밋에 들어갔다. Node 22로 옮겨 전 계층을 다시 돌릴 때
드러났다.

### 3. 대역(mock)이 실제보다 관대하면 그만큼이 사각지대다

e2e 앵커 대역이 **무엇을 주든 해석해 줬다.** 그래서 "맨 숫자 앵커" 결함(Codex
P1)이 CI 초록을 받았다. 지금은 대역이 서버와 같은 갈래로 판정한다(맨 숫자·

받아 주지는 않는가?**

### 4. 임시 컨테이너에서는 슬라이스마다 커밋하라

직전 웹 세션이 CR-030 캐스케이드를 커밋하지 않고 끝나 전부 유실됐다.

## 16. 통합 시험이 **전역 질의**를 쓰면 공유 DB에 오염된다 (3회 겪었다)

`prs_test`는 모든 시험 파일이 공유하고 `fileParallelism: false`라 순차 실행이지만,
**앞선 파일이 남긴 행은 그대로 있다.**

| 자리 | 증상 |
| --- | --- |
| `enqueueSnapshotBootstrap` 건수 단언 | 다른 저장소가 큐에 들어가 `1`이 아니라 `5` |
| `runCommitEnrichSweep` 배치 상한 | 다른 저장소가 500건을 채워 **내 커밋이 창에 못 들어옴** — 단독 실행은 통과, 전량 실행은 실패 |
| `upsertTeam` 픽스처 slug | `(org_id, slug)` 유니크에 다른 파일의 행이 걸림 |

→ **전역 건수로 단언하지 마라.** "내 저장소의 상태가 이렇게 됐는가"로 건다.
배치 상한이 걸리는 시험은 남의 행을 지우지 말고 **이미 처리된 것으로 표시**해
창에서 비운다(`commit-enrich.test.ts`의 `beforeEach` 참조).

## 17. ES `deleteByQuery` 앞에 `refresh`가 또 필요했다

`delete_by_query`는 **검색으로 대상을 찾는다.** `refresh: true`는 지운 *뒤에*
새로 고치는 옵션이라 이 문제를 풀지 않는다. WP-019가 CI에서 겪은 것과 같은 자리를
`commit-enrich.test.ts`에서 다시 밟았다.

## 18. 클래스 인스턴스를 스프레드하면 프로토타입 메서드가 사라진다

`{ ...mirrorGraph(), patchId: ... }`로 만든 대역은 나머지 메서드가 전부
`undefined`가 되고, 그 사실이 엉뚱한 자리에서 터진다. **명시적으로 위임하는
헬퍼**를 쓴다 (`commit-enrich.test.ts`의 `delegating`).

## 19. 실패를 빈 결과로 세면 폴백이 영원히 돌지 않는다

`MirrorCommitGraph.changedPaths`가 `code !== 0`을 `{ paths: [] }`로 삼켰다.
`FallbackCommitGraph`는 **던졌을 때만** 폴백하므로, 미러가 통째로 없어도
"변경 없음"이 정상 응답으로 보여 API로 넘어가지 않는다.
`readCommit`의 `null`도 같은 문제라 **`null`도 폴백 사유**로 만들었다.

→ **변경 없음(exit 0 + 빈 출력)과 읽지 못함(exit != 0)은 다른 사실이다.**

## 20. `diff-tree`는 병합 커밋에 대해 아무것도 내지 않는다

인자 하나로 부르면 부모가 둘 이상일 때 어느 쪽과 비교할지 정해지지 않아 **빈
출력**이다. `--root` 폴백도 마찬가지다. 그대로 두면 병합 커밋의 `changed_paths`가
조용히 빈 배열이 되고 경로 기반 조사가 거짓을 말한다. **첫 부모를 명시**한다
(`<sha>^1 <sha>`) — 이 제품의 세계관이 first-parent이고 GitHub API도 같은 기준이다.

## 21. 문서 검증 시험이 산문 언급으로 통과할 수 있다

## 39. 내가 내린 결정이 다른 실패 모드의 확률을 올렸는데 대가를 계산하지 않았다

## 40. 가드레일의 면제는 **파일 단위**다

ADR-008 `UNSCOPED_ALLOWLIST`는 경로 문자열이고 `packages/es/src/links.ts`가 `no_requester`로 올라 있다 — 사유는 "방아쇠가 이벤트와 잡이라 요청자가 없다"다. **사용자 대면 조회를 그 파일에 넣으면 그 사유를 그대로 물려받고 검사기는 아무것도 말하지 않는다.**

그 항목의 사유 문단이 **"사용자에게 내주는 관계 조회 API는 WP-031이 만들며 거기서 대상 범위를 다시 교집합해야 한다"**고 미리 적어 두었다는 점이 특히 뼈아프다 — 경고가 바로 그 자리에 있었다.

→ **면제 목록을 볼 때 "이 면제가 어느 범위에 걸리는가"를 물어라.** 그리고 새 성질의 코드는 면제된 파일 **밖**에 둔다.

같은 자리에서 세 번째 검사가 `msearch`·`count`·`scroll`·`openPointInTime`만 본다는 것도 드러났다 — **`get`·`mget`은 검사 대상이 아니었다.** 대상 내용을 `mget`으로 붙이는 구현이 그대로 통과했을 것이다. 넓혔되 `client.get`은 받지 않는다: Redis 핸들도 같은 이름을 쓴다(`apps/search-api/src/index.ts`).

## 41. e2e 귀속은 **되돌려서** 재라 — "diff 0" 근거를 못 쓰는 세션이 온다

## 60. **`open(path, 'w')`는 인자 검증보다 먼저 truncate한다**

## 78. 이름이 비슷한 버튼이 남의 시험을 모호하게 만든다

## 79. 빈 문자열로 치환하는 변이는 원복할 수 없다

→ **지우는 변이는 주석으로 치환하라.** 그리고 변이 실행 뒤에는 `git diff --stat`으로
원복을 확인한다 — 원복 실패는 조용하고, 그 뒤의 모든 판정을 오염시킨다.

## 구현이 옳아도 그것을 거는 시험이 없으면 다음 사람이 지운다

`FR-ING-009` AC-12(브랜치 추가가 채번을 요청한다)는 구현이 정확했는데 **거는 시험이 하나도 없었다.** `enqueueSequenceAssign`의 인자를 빈 배열로 바꿔도 통합 열아홉이 전부 초록이었다.

→ DoD 항목을 코드로 만족시킨 뒤 **"이 성질을 지금 깨면 무엇이 빨개지는가"를 물어라.** 답이 "아무것도"면 그 항목은 아직 완료가 아니다.

## 차분으로 세야 하는 시험을 절대값으로 세면 틀린다

채번 예약 시험을 처음에 "잡이 정확히 하나"로 썼다가 실패했다 — **등록 자체가 이미 하나를 예약했기 때문**이다. 조작 전후의 차이를 세도록 고쳤다.

→ "이 조작이 무엇을 더했는가"를 묻는 시험은 **조작 전 상태를 먼저 찍는다.** 절대값은 다른 경로가 같은 자원을 건드리는 순간 거짓이 된다.

## 시험이 리터럴 전문을 걸면 정당한 변경에 깨진다 — 또 밟았다

`registration-request.test.ts`가 열 목록 전문을 `toEqual`로 걸고 있었고, 마이그레이션 `020`이 처리 결과 열 넷을 정당하게 더하자 깨졌다 (`DEV-438`). `WP-039`가 `ACTIVE_AUDIT_ACTIONS`에서 배운 것과 **같은 자리**다.

→ **"무엇이 없어야 하는가"를 거는 편이 "목록이 정확히 무엇인가"보다 오래간다.** 전문을 걸어 두면 사람이 성질을 다시 보지 않고 목록만 갱신하고, 그 갱신이 언젠가 금지 값을 함께 들여보낸다.

## 한 함수 안에서 두 갈래가 갈릴 수 있다

`resolveJobTarget`의 `sequence_assign` 갈래는 슬러그 형식을 검사하는데 일반 갈래가 빠뜨렸다 (`DEV-437`). 파일이 갈라진 것이 아니라 **함수 하나 안에서** 갈렸다.

→ 같은 판정을 여러 갈래가 해야 하면 **그 대칭을 시험으로 센다.** 회귀가 이제 `if (owner === '' || name === '')`가 정확히 두 번 나타나는지 본다.

## CI 잡이 시작조차 하지 않는 실패가 있다

GitHub Actions가 계정 결제 문제로 잡을 띄우지 못했다 — `The job was not started because recent account payments have failed`. **단계가 0개이고 2초 만에 끝난다.**

→ 이것을 시험 실패로 읽으면 없는 결함을 쫓고, 반대로 실제 시험 실패를 이것으로 부르면 결함을 넘긴다. **`steps`가 비어 있고 주석이 결제를 말하면 잡이 뜨지 않은 것이다.** 재시도 1회로 확인한 뒤 로컬 배터리로 판정하고, 그 사실을 원장·PR·인계에 적는다.

## Playwright 라우트는 나중에 등록한 것이 먼저 매칭된다

`**/api/admin/jobs**`를 `**/api/admin/jobs/*`보다 **나중에** 등록했더니 그것이 `/jobs/11`의 `PATCH`까지 삼켜 제어 요청이 목록 응답을 받았다. 시험은 통과하면서 아무것도 지키지 않았다.

→ 경로가 겹치는 목은 **한 핸들러로 합치고 안에서 가른다.** 등록 순서에 기대면 그 순서를 아는 사람만 고칠 수 있다.

## Conductor 컴포넌트의 계약을 추측하지 마라

`StatusBadge`는 `status`·`icon`·`label`을 요구하고 `children`을 받지 않는다. `Meter`는 `valueText`가 필수다. `Table`은 `caption`을 prop으로 받는다. `Button.size`는 `sm`·`md`뿐이고 `variant`에 `danger`가 없다(`tone`이 그 자리다).

→ **`.d.ts`를 열어 보고 쓴다.** 이름이 익숙하다고 시그니처가 같지 않다.

## Radix 컴포넌트는 jsdom에 없는 API를 부른다

`Switch`가 `use-size`를 지나며 `ResizeObserver`를 만든다. `a11y/setup.ts`의 기존 포인터 API 폴리필과 같은 자리에 대역을 더했다.

→ 대역은 **아무것도 관찰하지 않는다.** 크기 반응을 흉내 내면 그 흉내가 실제와 다른 순간 시험이 거짓말을 한다 — 실제 동작은 e2e가 본다.

## 취소 시험을 상태 단언으로만 쓰면 절반만 지킨다 (PR #89 리뷰 P1)

이 세션은 "취소가 완료로 덮이지 않는다"를 잡 유형 다섯 전부에 걸고 통합 열여덟으로 증명했다. 그런데 그것은 **잡 행의 라벨**에 관한 성질이었고, **일이 실제로 멈추는가**는 묻지 않았다. 조정 스캔은 취소된 뒤에도 저장소를 계속 돌며 GHE를 불렀다 — **화면은 "취소됨"을 보이는데 비싼 스캔이 진행 중이었다.**

→ `DEV-436`이 고친 것과 `DEV-439`가 고친 것은 **같은 조작의 서로 다른 절반**이다. 하나는 기록을 지키고 다른 하나는 실행을 멈춘다. 취소를 다룰 때는 **둘 다** 묻는다: "상태가 보존되는가"와 "일이 멈추는가".

## 응답 필드를 좁히는 것과 변이를 막는 것은 다르다 (PR #89 리뷰 P2)

`allowedActionsForJob`가 `reconcile`에서 `pause`를 뺐지만 `PATCH`는 일반 전이표로 받았다. **직접 호출하는 클라이언트가 그것을 지나간다.**

→ 응답 필드가 "화면이 무엇을 그릴지"만 정하면 그것은 **안내**다. 화면이 그것을 믿어도 되게 하려면 **서버가 같은 판정을 변이 경로에서 강제**해야 한다. 판정을 한 곳에 모으는 것의 뜻은 "한 함수가 계산한다"가 아니라 "모든 경로가 그 함수를 지난다"이다.

## 양쪽을 같은 세션에서 만들면 어긋남이 시험에 나타나지 않는다 (PR #89 리뷰 P2)

화면이 `detail.job_id`를 읽도록 썼고 서버는 그것을 싣지 않았다. **e2e 목이 계약이 아니라 내 가정을 그대로 흉내 냈기 때문에** 시험이 초록이었다. `FR-ADMIN-002` AC-4가 명시적으로 그 필드를 요구하는데도 그랬다.

→ 목은 **계약 문서의 필드 이름을 보고** 만든다. 구현을 보고 만들면 구현의 실수를 그대로 복제한다. 그리고 서버 응답을 직접 단언하는 통합 시험을 **화면과 같은 세션에** 둔다.

## 계약이 정한 기본값을 구현이 빠뜨릴 수 있다 (PR #89 리뷰 P2)

`API-ADM-009` 계약이 "목록의 기본 필터가 `pending`"이라 적었는데 `parseRequestFilter`가 그것을 구현하지 않았다. **화면도 보내지 않아 두 자리가 함께 비어 있었다.**

→ 계약의 "기본값"·"optional"은 **구현해야 할 동작**이지 생략해도 되는 것이 아니다. 파서를 쓸 때 계약 문서의 그 줄을 열어 대조한다.

## PR 병합이 미해결 리뷰 0건을 뜻하지 않는다 — 또 확인했다

병합 직전에는 스레드가 0건이었고 **병합 뒤에 넷이 도착했다.** `WP-039`가 배운 것과 같은 자리이며, 병합 후 재확인이 그것을 잡았다.

→ 병합으로 세션을 끝내지 마라. `main` HEAD·열린 PR·**병합한 PR의 스레드**·CI를 다시 실측한다.


## 인계에 적은 SHA는 그 인계 커밋이 다시 옮긴다

세션 종료 인계는 **자기 자신이 `main`을 한 번 더 옮긴다.** `PR #91`까지를 적은 인계가 `PR #92`로 병합되자 그 안의 `main` 값이 즉시 낡았고, 이 인계도 같은 일을 겪는다.

→ 인계에 SHA를 적되 **"이 커밋이 옮긴다"를 함께 적는다.** 다음 에이전트는 `git rev-parse HEAD`로 실측하며, 그 안내를 `todos.md` 0절에 두었다.

## 전사는 저장소 루트에 두지 마라 — 규칙을 실측으로 확인한다

`.gitignore:24`의 `exports/`가 전사를 무시한다. 루트 경로는 **어떤 무시 규칙에도 걸리지 않아** `git add`에 휩쓸리며 `PR #77`·`#78`·`#79`가 그 실패를 기록해 두었다.

→ `/export` 뒤 `git check-ignore -v <경로>`로 **실제로 무시되는지 확인한다.** "규칙이 있을 것이다"로 넘기지 않는다. `.gitignore`를 `head -20`으로 잘라 보면 24행의 규칙을 놓친다 — 이번에 실제로 한 번 놓쳤다가 전문을 다시 읽고 찾았다.


## 여전히 유효한 것

- **CRLF 저장소** — 새 파일은 LF로 생기고, 파이썬 치환도 개행을 맞추지 않으면 조용히 0건이 된다. 이번 세션에서 멀티라인 치환 하나가 `SKIPPED (0)`으로 실패했고 그것을 확인하지 않았다면 "고쳤다"가 거짓이 되었을 것이다
- **e2e는 빌드를 하지 않는다** — 화면을 만든 뒤 `pnpm --filter @prs/web run build`가 먼저다
- **`git add -A`를 쓰지 않는다** — `agent-context/`가 tracked다
- **ID는 실측한다** — 연속의 다음이 비어 있다고 가정하지 마라

# 2026-08-31 세션이 추가한 것 (DEV-414 청산)

## 정정한 자리가 다음 리뷰의 첫 자리다

세 PR이 모두 자기 정정에 새 지적을 받았고 **전부 실결함**이었다 — `PR #94`가 `#91`의 정정에, `PR #95`가 `CR-056`의 구현에, design-system `PR #12`가 그 자체의 정정에.

→ **정정 PR을 병합으로 끝내지 마라.** 방금 고친 자리가 다음 리뷰의 첫 자리다.

## 문장으로 쓴 근거는 코드로 확인하기 전까지 결함 후보다

같은 세션에서 양방향으로 겪었다.

- `DEV-443`: 이전 주석이 "저장소 중간에 끊으면 되돌리기가 부분으로 남는다"고 적었는데 **재개 커서가 없어** 그 근거가 성립하지 않았다. 코드로 확인해 경계를 넓혔다
- `DEV-455`: 드릴다운을 "갈아 끼운다"고 정하며 이유를 적었는데 **집계가 세는 것이 이미 교집합**이라 정확히 반대였다. 확인하지 않고 쓴 문장이 그대로 결함이 됐다

→ 주석의 근거를 그대로 믿지 말고, **자기가 쓸 근거도 코드로 먼저 확인하라.**

## 판정 재료를 좁히는 일은 한 번에 끝나지 않는다

모름의 재료가 세 번 바뀌었다: `enrichment_pending && files.length === 0` → `enrichment_pending` → `enrichment_errors`의 `files` 항목. 첫 번째 정정은 **기존 시험**이, 두 번째는 **리뷰**가 잡았다.

→ 좁힌 뒤에도 **그 재료가 무엇을 포함하는지** 다시 묻는다. `enrichment_pending`은 네 구성 요소 중 하나만 실패해도 참이다.

## 개수 단언은 무엇이 늘었는지 말하지 않는다 — 세 번째다

지원 키를 "17종"으로 세는 자리가 **단위 하나와 통합 둘**에 흩어져 있었다. `CR-054`(감사 대상 개수)와 `DEV-438`(열 목록 전문)에 이어 같은 유형이다.

→ 개수를 걸지 말고 **정본 목록과 대조하라.** 실패 메시지가 어느 항목인지 보여 준다. 단, "구간이 늘었다는 사실 자체를 검토하게 하는" 목록 단언은 성격이 다르므로 유지한다.

## 필드를 싣지 않는 것과 지우는 것은 다르다

조건부 업서트(`CONDITIONAL_UPSERT_SCRIPT`)는 `params.doc`에 **실린 키만** 대입한다. 투영이 필드를 빼도 이미 색인된 값이 그대로 남는다.

→ **부재로 판정하는 필드는 부재를 실제로 만들 수 있어야 한다.** `UpsertRequest.remove`가 그 자리다.

## 계약을 고치는 것과 데이터를 고치는 것은 다른 일이다

`CR-056`이 계약과 투영을 고쳤는데 **이미 색인된 문서**는 그대로였다. 원장이 "소급한다"고 적었는데 그 작업이 커밋에 없었다(`DEV-456`).

→ 판정 재료를 바꾸는 정정은 **기존 데이터의 마이그레이션까지가 범위다.** 재구성 경로가 새 판정을 지나는지도 함께 확인한다.

## 완전해야만 옳은 목록은 잘못된 모양이다

릴리스 태그 검증에서 "패키지 디렉터리 변경"을 비교했더니, CSS 빌드가 tokens 산출물을 임베드하고 모든 빌드가 `pnpm-lock.yaml`을 읽는다는 지적을 받았다. **"산출물에 영향을 주는 모든 입력"은 빌드 그래프가 바뀌는 첫 순간 낡는 목록이다.**

→ 목록 대신 **불변식**을 걸었다: 태그는 릴리스 HEAD를 가리킨다.

## CI 상태는 저장소마다 확인한다

pr-search는 계정 결제로 잡이 시작조차 하지 않는데(`steps=0`), **design-system은 27단계를 정상 통과했다.** 이전 세션들의 "CI가 죽어 있다"는 기록은 한 저장소 이야기였다.

## 개발 타입이 지원 범위보다 좁으면 그만큼이 사각지대다

design-system은 React 19 타입으로 개발하는데 peer range에 React 18이 있다. `ReactNode` 반환 타입이 React 18에서 JSX 컴포넌트로 부적격이라는 것을 **타입 검사도 시험도 보지 못했다.**

## 여전히 유효한 것

- **CRLF 저장소** — 치환은 `APPLIED (1)`을 확인한다
- **e2e는 빌드를 하지 않는다**
- **`git add -A`를 쓰지 않는다** — `agent-context/`가 tracked다
- **ID는 실측한다**
- 통합 시험 파일은 **자기가 남긴 상태를 지우고 끝낸다** — `beforeEach`의 `TRUNCATE`는 파일 안에서만 성립하며, 남은 `queued` 잡을 다른 파일의 `claimNextJob`이 집는다

## 사용처가 있다는 것과 그 조건에 닿는다는 것은 다르다

design-system 정정 뒤 "PR Search가 `Select.Root`와 `IconButton`을 쓴다"만 확인하고 **결함 조건**은 보지 않았다. 실측하니 `IconButton` 두 곳 모두 `loading`을 넘기지 않고 `Select.Root`는 `Field` 밖이라 **어느 쪽도 닿지 않았다.** 그 문구를 그대로 뒀다면 다음 작업자가 불필요한 npm 게시와 의존성 갱신을 사용자에게 요청했을 것이다.

→ 소비 영향을 말할 때는 **그 props/context가 실제로 전달되는지**까지 본다. import 목록은 사용처이지 조건이 아니다.

## 릴리스 불변식은 실제 릴리스로 확인한다

`check-release-tags.mjs`를 "태그가 릴리스 HEAD를 가리켜야 한다"로 바꿨는데, 개발 브랜치에서 돌리면 실패하므로 **정당한 릴리스를 막는지는 알 수 없었다.** `0.2.1` 게시가 그것을 확인했다 — `verify local release tags`와 `verify pushed release tags`가 모두 통과했고, `linked` 설정 덕에 세 태그가 같은 커밋에 생긴다는 근거가 실제로 성립했다.

→ 릴리스 경로의 검사는 **릴리스가 한 번 돌아야 검증된다.** 그때까지는 "막지 않을 것이다"가 아니라 "막는지 아직 모른다"로 적는다.
