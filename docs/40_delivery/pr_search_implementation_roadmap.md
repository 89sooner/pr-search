# PR Search 구현 로드맵

> 상태: review | 버전: v0.2 | 갱신일: 2026-08-19

## 1. 목적

승인된 요구사항과 아키텍처를 실제 구현 가능한 vertical slice와 milestone으로 분해한다. 각 REL은 `pr_search_work_packages.md`에서 WP로 다시 분해된다. 이 문서는 범위를 추가하지 않는다.

## 2. 원칙

- 각 슬라이스는 요구사항, 화면, API, 데이터, 테스트, 운영 준비를 함께 가진다.
- UI만 구현하거나 API만 구현한 상태를 완료로 보지 않는다.
- 선행 의존성을 명시하고, 위험한 결정은 ADR로 연결한다.
- **각 릴리스는 그 자체로 사용자에게 가치를 준다.** REL-002가 끝나면 조직은 이미 "SHA로 PR 찾기"를 실제로 쓸 수 있어야 한다. 전부 완성될 때까지 아무것도 못 쓰는 계획은 세우지 않는다.

## 3. 릴리스 순서의 근거

이 제품의 가치는 두 축이다: **양방향 식별자 해석**과 **머지 시퀀스**. 둘 중 어느 것도 관계 그래프나 통계 없이 단독으로 유용하다. 따라서 순서는 다음과 같이 잡는다.

1. 파이프라인이 먼저다. 데이터가 없으면 아무 기능도 검증할 수 없다 (REL-001).
2. 양방향 해석이 그다음이다. 가장 자주 쓰이고, 시퀀스 없이도 동작한다 (REL-002).
3. 시퀀스와 범위 조사가 세 번째다. Perforce 전환 문제의 직접 해답이며, 커밋 그래프 인프라를 요구한다 (REL-003).
4. 관계와 전문 검색은 조사 경로를 넓힌다 (REL-004).
5. 통계와 운영 고도화는 관리자 수요를 채운다 (REL-005).
6. 그래프 시각화와 조사 보조는 마지막이다 (REL-006).

권한 강제(FR-AUTH-002)만은 예외적으로 REL-002에 들어간다. 검색이 처음 열리는 순간부터 접근 통제가 있어야 하며, 나중에 얹는 접근 통제는 반드시 구멍을 남긴다.

## 8. 마이그레이션 계획

이 제품은 기존 시스템을 대체하지 않으므로 데이터 마이그레이션이 아니라 **초기 적재** 문제다.

| 단계 | 시점 | 내용 |
| --- | --- | --- |
| 1 | REL-001 완료 후 | 파일럿 저장소 3개 등록, 실시간 수집만 (백필 없음) |
| 2 | REL-002 완료 후 | 파일럿 저장소 백필 (과거 전체). 소요 시간과 API 소모 실측 |
| 3 | REL-003 완료 후 | 파일럿 저장소 시퀀스 전체 채번. git 대조 검증 |
| 4 | REL-003 검증 후 | 핵심 저장소 30개로 확대. 사용자 베타 시작 |
| 5 | REL-005 완료 후 | 전체 저장소 등록. 백필은 우선순위 순으로 점진 진행 |

**백필은 한 번에 하지 않는다.** 3000개 저장소를 동시에 백필하면 GHE API 한도를 소진하고 실시간 수집까지 밀린다. 저장소별로 큐에 넣고 동시 3개씩 진행한다 (FR-ING-006 AC-6).

## 9. Known Limitations

| REL-001~002 동안 시퀀스가 없어 범위 조사가 불가하다 | 초기 사용자는 SHA↔PR 해석만 사용 | REL-003 | 승인 (릴리스 순서의 의도된 결과) |
