# PR Search 구현 로드맵

> 상태: review | 버전: v0.14 | 갱신일: 2026-09-02

## 1. 목적

승인된 요구사항과 아키텍처를 실제 구현 가능한 vertical slice와 milestone으로 분해한다. 각 REL은 `pr_search_work_packages.md`에서 WP로 다시 분해된다. 이 문서는 범위를 추가하지 않는다.

## 2. 원칙

- 각 슬라이스는 요구사항, 화면, API, 데이터, 테스트, 운영 준비를 함께 가진다.
- UI만 구현하거나 API만 구현한 상태를 완료로 보지 않는다.
- 선행 의존성을 명시하고, 위험한 결정은 ADR로 연결한다.
- **각 릴리스는 그 자체로 사용자에게 가치를 준다.** REL-002가 끝나면 조직은 이미 "SHA로 PR 찾기"를 실제로 쓸 수 있어야 한다. 전부 완성될 때까지 아무것도 못 쓰는 계획은 세우지 않는다.

## 3. 릴리스 순서의 근거

이 제품의 가치는 두 축이다: **양방향 식별자 해석**과 **머지 시퀀스**. 둘 중 어느 것도 관계 그래프나 통계 없이 단독으로 유용하다. 따라서 순서는 다음과 같이 잡는다.

1. 파이프라인이 먼저다. 데이터가 없으면 아무 기능도 검증할 수 없다 (REL-001).
2. 양방향 해석이 그다음이다. 가장 자주 쓰이고, 시퀀스 없이도 동작한다 (REL-002).
3. 시퀀스와 범위 조사가 세 번째다. Perforce 전환 문제의 직접 해답이며, 커밋 그래프 인프라를 요구한다 (REL-003).
4. 관계와 전문 검색은 조사 경로를 넓힌다 (REL-004).
5. 통계와 운영 고도화는 관리자 수요를 채운다 (REL-005).
6. 그래프 시각화와 조사 보조는 마지막이다 (REL-006).

권한 강제(FR-AUTH-002)만은 예외적으로 REL-002에 들어간다. 검색이 처음 열리는 순간부터 접근 통제가 있어야 하며, 나중에 얹는 접근 통제는 반드시 구멍을 남긴다.

### 4.1 첫 사내 반입 마일스톤 (CR-059 / ADR-021)

**이것은 새 `REL`이 아니다.** `REL-###`은 요구사항 슬라이스이고 여기서 정하는 것은 **이미 승인된 요구사항을 사내에 세우는 경로**다. 새 요구사항이 없으므로 새 슬라이스 번호를 만들지 않는다.

```text
현재 (REL-006 진행 중, WP-041·WP-069 done)
        ↓
WP-070  단일 호스트 오프라인 배포·반입 기반          done (2026-09-01)
        ↓
──────── 첫 사내망 반입 가능선 ────────
        ↓
WP-071  사내 반입 운반 아카이브와 실행 절차 정본화    done (2026-09-02, CR-062)
        ↓
──────── 사내에서 그대로 실행 가능한 반입 지침 ────────
        ↓
WP-072  운반 경로 — GitHub Release 발행·사내 다운로드     todo (CR-063 · 사내 outbound 확인 2026-09-02)
        ↓
실제 사내 single-host bring-up (사내에서만 실행 가능)
        ↓
실 GHE 저장소 1~3개 파일럿 · 인증·도메인 정확성 증거
```

**`WP-071`은 `WP-070`의 후속이며 역시 새 `REL`이 아니다** (CR-062). 가능선이 섰다는 것과 처음 보는 사내 운영자가 외부에서 전달받은 **파일 하나**로 런북을 위에서 아래로 실행해 반입을 시작할 수 있다는 것은 같은 주장이 아니다 — `WP-070`의 여정은 실행자가 그 자리에서 조립한 명령으로 관통됐고, 운반 단위와 사내 쪽 첫 명령들이 정본화되지 않았다(DEV-523·DEV-524). `WP-071`이 그 빈칸을 닫으며, `REL-006` 완료율에는 넣지 않는다.

**`WP-072`는 운반 경로만 바꾼다** (CR-063). 결정자가 사내 어느 위치에서든 github.com에 닿는다고 확인하면서(`DEV-528`) "조직의 반입 절차 / 물리적 이동"으로만 적혀 있던 경계가 GitHub Release 자산 다운로드로 정해진다. 번들·설치 절차·계보는 `WP-071` 그대로이며, 역시 새 `REL`이 아니고 `REL-006` 완료율에 넣지 않는다.

**반입 대상은 read-only Search/Investigation Plane이다.** `REL-007`~`REL-011`의 GitHub Operations Plane은 **첫 반입의 blocker가 아니며** `gh-executor`를 파일럿 기본 형상에 넣지 않는다 (인프라 3.1장).

**`REL-006`의 잔여 WP는 이 마일스톤보다 뒤다.** `WP-042`(이분 탐색)·`WP-044`(내보내기)의 요구사항은 둘 다 `Could` 등급이고, `WP-043`은 `ACC-06`이 `NOT RUN`이라 착수 조건 자체가 성립하지 않는다. **반입 가능선을 먼저 세우는 것이 이 시점의 우선순위다** — 기능을 하나 더 만드는 것보다 **지금까지 만든 것을 사내에서 실제로 쓸 수 있게 만드는 것**이 앞선다.

**외부망에서 증명할 수 없는 것은 이 마일스톤에서 증명하지 않는다.** 사내 GHE·OIDC·CA·프록시·DNS·실서버 성능은 `NOT RUN — internal environment required`로 남기며, 합성 데이터로 통과시키지 않는다. `ACC-06`도 마찬가지다.

## 8. 마이그레이션 계획

이 제품은 기존 시스템을 대체하지 않으므로 데이터 마이그레이션이 아니라 **초기 적재** 문제다.

| 단계 | 시점 | 내용 |
| --- | --- | --- |
| 1 | REL-001 완료 후 | 파일럿 저장소 3개 등록, 실시간 수집만 (백필 없음) |
| 2 | REL-002 완료 후 | 파일럿 저장소 백필 (과거 전체). 소요 시간과 API 소모 실측 |
| 3 | REL-003 완료 후 | 파일럿 저장소 시퀀스 전체 채번. git 대조 검증 |
| 4 | REL-003 검증 후 | 핵심 저장소 30개로 확대. 사용자 베타 시작 |
| 5 | REL-005 완료 후 | 전체 저장소 등록. 백필은 우선순위 순으로 점진 진행 |

**백필은 한 번에 하지 않는다.** 3000개 저장소를 동시에 백필하면 GHE API 한도를 소진하고 실시간 수집까지 밀린다. 저장소별로 큐에 넣고 동시 3개씩 진행한다 (FR-ING-006 AC-6).
