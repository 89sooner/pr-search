## 2. 제품 목표

Perforce에서 GitHub Enterprise로 전환하면서 잃어버린 **"단조 증가하는 반영 순서"** 를 되돌려 주고, PR과 커밋을 서로 역추적할 수 있는 사내 검색·분석 대시보드를 제공한다.

Perforce의 Changelist(CL) 번호는 submit 시점에 채번되므로 `번호 순서 = 반영 순서`가 보장되었다. 그래서 "CL 12000까지는 검증됐다", "12100~12250 구간을 조사하라" 같은 소통이 성립했다. GitHub PR 번호는 **생성 시점** 채번이므로 PR #105가 PR #98보다 먼저 머지될 수 있고, 같은 소통이 성립하지 않는다.

PR Search는 이 격차를 세 가지로 메운다.

1. **머지 시퀀스(Merge Sequence)**: (저장소, 브랜치)마다 target 브랜치 first-parent 히스토리의 서수를 부여해 CL과 동일한 의미의 단조 증가 번호를 복원한다.
2. **양방향 식별자 해석**: 커밋 SHA → PR, PR → 커밋을 모두 단일 조회로 해결한다.
3. **관계 그래프**: 선행/후행, 포함, 참조, 되돌림, 체리픽, 스택, 동시 변경 관계를 명시적 간선으로 저장한다.

이 위에 Elasticsearch 기반의 필터링·정렬·그룹핑·집계 대시보드를 얹어, 관리자가 GitHub UI 질의 문법을 배우지 않고도 배포 구간과 조직 지표를 확인하도록 한다.

### 2.1 비목표 (Non-goals)

- GitHub Enterprise를 대체하지 않는다. PR 생성/리뷰/머지 등 쓰기 행위는 GHE에서만 일어나며, PR Search는 읽기 전용 파생 시스템이다.
- 코드 리뷰 도구, 정적 분석, 취약점 스캐너가 아니다. diff 본문 자체를 저장·검색하지 않는다(변경 경로와 규모만 저장한다).
- CI/CD 실행기가 아니다. 빌드·테스트를 트리거하지 않고, 릴리스 앵커 정보를 소비만 한다.
- 개인 평가 도구가 아니다. 집계는 팀·저장소 단위까지만 제공하고 개인 순위표는 제공하지 않는다(F-STAT-007 제외).
- Perforce 데이터를 마이그레이션하지 않는다. 전환 이전 CL 히스토리는 범위 밖이다.

### 5.3 GitHub Operations Plane (CR-005 신규)

2026-08-20 사용자 승인으로 제품에 두 번째 축이 추가되었다. 조사에서 나온 결론을 실행으로 옮기는 일 — PR 머지, 이슈 생성, 워크플로 재실행, 릴리스 발행 — 이 지금은 터미널의 `gh`에서만 가능하고 웹 대시보드는 조사에서 끊긴다. Operations Plane은 그 단절을 없앤다.

| 항목 | 내용 |
| --- | --- |
| 목표 | `gh` CLI가 지원하는 GitHub 작업을 웹에서 구성·실행. 터미널에서 조합할 수 있는 command/flag/argument를 웹에서 동등하게 표현한다. CR-008에서 그 "동등"의 기준을 28개 parity 차원으로 확정했다 — command path와 flag 목록만으로는 동등이 아니다 (SRS §9.8) |
| 접근 방식 | 화면을 명령마다 손으로 만들지 않는다. 버전 고정된 capability manifest에서 UI를 **생성**하고, 자주 쓰는 업무만 전용 화면으로 다듬는다 |
| 완전성 기준 | 고정 gh 버전의 모든 command path와 문서화된 flag가 분류되어 있을 것. 미분류 0 (NFR-009) |
| 안전 원칙 | 임의 shell 없음. 고정 바이너리 + manifest에서 조립한 argv만 실행. 위험도별 확인·승인. 모든 실행 감사 |
| 신원 | 수집용 App과 분리된 Operations App. 사용자 위임 토큰. 유효 권한은 App 권한 ∩ 사용자 권한 |
| 우선순위 | Search/Data Plane(REL-001~006)이 end-to-end로 닫힌 뒤 시작 |

**CR-008에서 강화한 세 가지 (2026-08-20).** 범위를 넓힌 것이 아니라 기준을 엄격하게 만든 것이다.

1. **유효 조합의 정의가 한 곳에만 있다.** manifest의 의미 제약 모델을 폼·서버 검증·argv 빌더·테스트 생성기가 함께 읽는다. 클라이언트를 우회해 API를 직접 불러도 서버가 같은 사유로 거부한다.
2. **`terminal_only`는 마지막 분류다.** 터미널 UX와 기능 의미를 나눠서 웹 등가를 먼저 찾는다. `gh browse`는 서버에서 브라우저를 띄우는 것이 아니라 URL을 돌려주는 것이 옳은 구현이다.
3. **gh 출력을 신뢰하지 않는다.** PR 제목·브랜치 이름·파일 경로는 아무나 쓸 수 있는 외부 입력이고, gh 2.97.0 자신도 그 처리에서 보안 수정을 한 이력이 있다. 모든 출력은 무해화 경계를 통과한 뒤에만 화면에 닿는다.

**CR-009에서 넓힌 것 (2026-08-20).** CR-008이 "한 명령의 모든 유효 조합"을 닫았다면, CR-009는 "여러 명령을 이어 만드는 유효한 작업"을 닫는다.

실제 업무는 명령 하나로 끝나지 않는다 — 검색해서 고르고, 고른 것의 상태를 보고, 받은 파일을 다음에 넘긴다. 그런데 gh 출력이 전부 JSON은 아니라서, "이전 단계 JSON에서 필드 뽑기"만으로는 이 연결이 표현되지 않는다. 그래서 **출력에도 계약**을 두고, 어떤 명령을 이을 수 있는지를 **타입으로 계산**한다. 명령 쌍마다 특수 코드를 넣지 않는다.

여기서 하나 분명히 한다. `gh auth token`은 값 자체가 자격 증명이다. 조합을 일반화하면서 이것을 "문자열을 반환하는 명령"으로 취급해 다음 단계에 자동으로 이어 주면, 편의 기능이 그대로 유출 경로가 된다. **기능이 존재한다는 사실과 비밀 값을 노출하는 것은 다른 문제다** — capability는 목록에 있고 실행되지만, 그 결과는 흐르지 않는다.

첫 사용자 가치는 라이브러리가 아니라 화면이다. 최초 수직 슬라이스가 끝나면 사용자는 웹에서 저장소를 고르고, capability를 고르고, 옵션을 넣고, 실행될 argv를 확인하고, 실행하고, 결과와 이력을 볼 수 있어야 한다. 초기에는 R0 읽기 전용 capability만 열어도 된다.

### 5.4 Out of Scope

| 제외 항목 | 사유 |
| --- | --- |
| PR 생성·리뷰·머지 등 GHE 쓰기 행위 | PR Search는 읽기 전용 파생 시스템이다. 쓰기 경로를 두면 GHE와 권한/감사 이중화가 발생한다 |
| diff 본문(패치 텍스트) 저장 및 코드 검색 | 저장 용량과 소스 유출 위험이 크고, GHE 코드 검색이 이미 존재한다. 변경 경로와 라인 수만 저장한다 |
| 빌드·테스트 실행, 자동 이분 탐색 실행 | CI 시스템의 역할이다. PR Search는 후보 구간과 다음 검사 지점만 제시한다 |
| Perforce CL 히스토리 마이그레이션 | 전환 이전 데이터는 P4 서버에서 조회한다 |
| 개인 단위 생산성 순위표 | 인사 평가 오남용 위험 (F-STAT-007 제외 결정) |
| Issue/Project/Discussion 도메인 | 1차 목표는 PR·커밋 추적이다. 이슈는 참조 관계의 대상 ID로만 다룬다 |
| 저장소 간 통합 단일 시퀀스 | 저장소 사이에는 인과 순서가 없어 번호가 의미를 갖지 못한다 (F-SEQ-008 제외 결정) |
| 모바일 전용 앱 | 데스크톱 브라우저 반응형으로 충분하다 |

## 6. 핵심 사용자 시나리오

### SCN-002 배포 구간 조사

- 시작 조건: `build-20260812-03`에서는 정상이었고 `build-20260814-01`에서 장애가 발생했다.
- 기본 흐름: 릴리스 매니저가 범위 조사 화면에서 두 릴리스를 앵커로 지정한다 → 시스템이 앵커를 머지 시퀀스 값으로 정규화한다 → 구간에 포함된 PR 목록을 머지 순서대로 반환한다 → 작성자·팀·라벨·경로 패싯으로 후보를 좁힌다 → 구간이 커도 커서로 끝까지 훑는다.
- 대체 흐름: 릴리스 태그 대신 SHA, PR 번호, 날짜 구간을 앵커로 지정해도 동일한 결과를 얻는다.
- 대체 흐름: 검색 화면에서 `repo:acme/payments base:main seq:1280..1342`처럼 질의로 같은 구간을 본다. **이때도 저장소와 대상 브랜치를 함께 지목해야 한다** — 서수는 그 조합 안에서만 뜻이 있고, 지목하지 않으면 여러 저장소의 같은 번호가 한 목록에 섞인다. 조사 결과의 주소를 동료에게 보내면 그 주소는 **어느 히스토리 세대의 번호였는지**까지 함께 전달한다 (CR-051).
- 오류 흐름: 두 앵커가 서로 다른 브랜치에 속하면 비교를 거부하고 브랜치 선택을 요구한다.
- 오류 흐름: 받은 주소를 열었을 때 그 사이에 히스토리가 재작성됐으면 **결과를 보여 주지 않고** 번호의 뜻이 달라졌다는 사실과 두 세대의 값을 알린다. 사용자가 「현재 에폭으로 다시 조회」를 눌러야 새 세대의 결과를 본다 — **시스템이 대신 옮기면 같은 번호가 다른 커밋을 가리키는 답을 오류 없이 받게 된다** (CR-051).
- 관련 요구사항: FR-SEQ-002, FR-SEQ-003, FR-SEQ-004, FR-SEQ-005, FR-SRCH-005, FR-SRCH-006, FR-SRCH-009

### SCN-003 문제 PR의 선행·후행 확인과 후보 좁히기

- 시작 조건: 의심 PR 1건을 특정했지만 확신이 없다.
- 기본 흐름: PR 상세에서 동일 브랜치 머지 시퀀스 기준 선행 10건·후행 10건을 확인한다 → 이분 탐색 보조에서 good/bad를 표시하며 후보 구간을 절반씩 줄인다 → 남은 후보를 확정한다.
- 대체 흐름: 되돌림 관계가 이미 존재하면 revert PR을 즉시 표시해 조사 자체를 종료한다.
- 오류 흐름: 대상 PR이 미머지 상태여서 시퀀스가 없으면 선행·후행 탐색을 비활성화하고 사유를 표시한다.
- 관련 요구사항: FR-REL-001, FR-REL-004, FR-SEQ-007

### SCN-004 이 PR이 어느 배포에 들어갔는가

- 시작 조건: 고객 문의에 대응하려면 특정 PR의 배포 시점을 알아야 한다.
- 기본 흐름: PR 상세에서 "포함된 릴리스" 섹션을 확인한다 → 해당 PR의 머지 커밋을 포함하는 태그·릴리스 목록과 각 릴리스 시각을 본다.
- 대체 흐름: 아직 어떤 릴리스에도 포함되지 않았으면 "미배포" 상태와 대상 브랜치 head까지의 대기 PR 수를 표시한다.
- 오류 흐름: 릴리스 앵커가 수집되지 않은 저장소면 사유와 등록 경로를 표시한다.
- 관련 요구사항: FR-REL-002, FR-SEQ-004

### SCN-005 조직 지표 확인

- 시작 조건: 관리자가 월간 리뷰를 준비한다.
- 기본 흐름: 통계 대시보드에서 기간·조직을 지정한다 → 팀별 머지 PR 수, 리드타임 백분위, 리뷰 대기 시간, 변경 규모 분포를 확인한다 → 특정 팀을 눌러 해당 조건이 적용된 검색 결과로 이동한다.
- 대체 흐름: 검색 결과 화면에서 현재 질의 위에 바로 집계를 실행한다.
- 대체 흐름: 월간 리뷰마다 되풀이하는 조회 조건을 이름과 함께 저장하고, 다음 리뷰에서 그것을 그대로 재실행한다. 같은 조건을 함께 쓰는 팀이 있으면 그 팀 하나를 대상으로 지정해 공유하며, 공유받은 구성원은 조회와 실행만 하고 결과는 언제나 실행한 사람의 접근 범위로 계산된다 (CR-049).
- 오류 흐름: 집계 대상 문서 수가 상한을 넘으면 표본 기반 근사임을 표시한다.
- 오류 흐름: 저장해 둔 질의가 이후 문법 변경으로 해석되지 않으면 실행을 막고 오류 위치를 보여 준다. 고치는 것은 저장자의 몫이며 시스템이 대신 바꾸지 않는다 (CR-049).
- 관련 요구사항: FR-STAT-001~006, FR-SRCH-006, FR-SRCH-010

### SCN-006 수집 지연 대응

- 시작 조건: 운영자가 "검색 결과에 방금 머지한 PR이 없다"는 문의를 받았다.
- 기본 흐름: 운영 콘솔에서 큐 적체·처리 지연·DLQ 건수를 확인한다 → 원인 이벤트를 DLQ에서 조회한다 → 원인 해소 후 재처리한다.
- 대체 흐름: 웹훅 자체가 누락된 경우 해당 저장소 조정 스캔을 실행해 누락분을 채운다.
- **대체 흐름(사용자 자가 진단)**: 문의가 운영자에게 닿기 전에 사용자가 저장소 개요에서 스스로 확인한다 → 자기 접근 범위 안 저장소의 등록 상태·마지막 수집 시각·문서 수·백필 상태·시퀀스 공간 상태·최근 완료된 조정 스캔의 누락 건수를 본다 → **"권한이 없다 / 등록되지 않았다 / 수집이 늦다" 셋을 구분한다.** 이 화면은 조회만 하며 등록·백필·재채번을 실행하지 않는다. 문제가 등록 자체이면 등록 검토 요청을 남기고, 수집 지연이면 기본 흐름의 운영자 경로로 이어진다.
- **대체 흐름(미등록 저장소)**: 찾는 저장소가 목록에 없으면 사용자가 `owner/name`으로 등록 검토 요청을 남긴다 → 요청은 기록될 뿐 등록·수집을 시작하지 않으며, **대상 저장소가 실제로 있는지도 확인하지 않는다** → 운영자가 A-002에서 그 요청을 보고 실제 등록 여부를 판단한다.
- 오류 흐름: 재처리가 재차 실패하면 이벤트를 보류 상태로 유지하고 알림을 발생시킨다.
- **오류 흐름(부분 실패)**: 저장소 개요의 진단 항목 하나가 조회에 실패하면 그 항목만 미확인으로 표시하고 나머지는 그대로 보여 준다 — 카드 전체를 오류로 만들면 사용자가 확인하러 온 다른 사실까지 잃는다.
- 관련 요구사항: FR-ING-006, FR-ING-007, FR-ING-009, FR-ING-011, FR-SEQ-001, FR-SEQ-005, FR-AUTH-002, FR-ADMIN-001, FR-ADMIN-002

### SCN-007 되돌림·체리픽 추적

- 시작 조건: 릴리스 브랜치에 핫픽스가 반영됐는지 확인해야 한다.
- 기본 흐름: PR 상세의 관계 섹션에서 체리픽 대응 커밋과 대상 브랜치를 확인한다.
- 대체 흐름: 대응 커밋이 없으면 "백포트 누락 후보"로 표시한다.
- 오류 흐름: 충돌 해결로 diff가 달라져 자동 탐지에 실패하면 신뢰도 표기와 함께 참조 트레일러 기반 후보만 제시한다.
- 관련 요구사항: FR-REL-004, FR-REL-005

## 9. 아키텍처 및 실행 환경 가정

- 구현 언어는 프런트엔드·백엔드·배치 전 계층 TypeScript로 통일한다 (ADR-001).
- 검색 엔진은 Elasticsearch 8.x이며, 검색·집계의 단일 질의 대상이다 (ADR-003).
- 원본 이벤트와 시퀀스 상태는 PostgreSQL을 시스템 오브 레코드로 사용하고, Elasticsearch 인덱스는 언제든 재구성 가능한 파생 뷰로 취급한다 (ADR-004).
- 이벤트 전달은 Redis Streams 기반 작업 큐로 시작하고, `EventBus` 포트 뒤에서 Kafka로 교체 가능하게 설계한다 (ADR-002).
- 불변 원본 이벤트 아카이브 레인만 Filebeat로 Elasticsearch에 직접 적재한다. 엔티티 인덱스 레인은 애플리케이션 워커가 담당한다 (ADR-002).
- 웹 대시보드는 사내 `design-system`(Conductor) 패키지 `@conductor-by-89soone/tokens`, `@conductor-by-89soone/css`, `@conductor-by-89soone/react`를 사용한다 (ADR-006).
- GitHub Enterprise는 이미 사내 웹훅 구독이 구성되어 있으며, PR은 Squash & Merge 단일 정책이다.
- 배포 대상은 사내 Kubernetes 클러스터이며 인터넷 노출은 없다.

## 11. 릴리스 전략

- P0 (REL-001~REL-003): 수집 파이프라인, 양방향 식별자 해석, 머지 시퀀스와 범위 조회, 릴리스 구간 비교, 권한 필터링, 기본 검색 화면
