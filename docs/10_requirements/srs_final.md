## 1. 문서 개요

- 문서명: PR Search 최종 요구사항 정의서
- 문서 성격: 최종 SRS 겸 구현 기준 문서
- 기준 문서: `feature.md`, `prd.md`, `workflow.md`, `glossary.md`
- 우선순위: 이 문서가 최상위 제품 진실이다. 파생 UI 문서, 아키텍처 문서, 딜리버리 문서는 이 문서를 번역하고 포장할 뿐 범위를 추가하지 못한다.

## 2. 통합 결론

PR Search는 GitHub Enterprise의 PR·커밋 데이터를 웹훅으로 수집해 Elasticsearch에 색인하고, 다음 세 가지를 제공하는 사내 읽기 전용 검색·분석 시스템이다.

1. **머지 시퀀스**: (저장소, 대상 브랜치)마다 first-parent 히스토리 서수를 부여해 Perforce Changelist와 동일한 의미의 단조 증가 번호를 복원한다. 이것이 "이 번호까지는 검증됐다", "이 구간을 조사하라"는 조직의 기존 소통 방식을 되살리는 핵심 장치다.
2. **양방향 식별자 해석**: 커밋 SHA로 PR을, PR로 커밋을 각각 단일 조회로 찾는다. 축약 SHA, PR 번호, GHE URL을 구분 없이 하나의 입력창에서 받는다.
3. **관계 그래프**: 선행/후행, 포함, 참조, 되돌림, 체리픽, 스택, 동시 변경 관계를 명시적 간선으로 저장해 조사 경로를 이어 준다.

이 위에 다차원 필터링, 정렬, 그룹핑, 시계열·분포 집계를 제공하는 웹 대시보드를 얹는다.

## 3. 제품 비전과 목표

### 3.1 제품 비전

형상 관리 시스템이 Perforce에서 Git으로 바뀌어도, "언제 무엇이 들어갔고 어디까지가 안전한가"에 대한 조직의 답변 능력은 그대로 유지되어야 한다. PR Search는 Git의 분산·비선형 특성을 감추지 않으면서도, 조사와 소통에 필요한 **단일 순서 축**을 복원한다.

여기에 v2.0(CR-005)에서 두 번째 축이 더해졌다. 조사에서 얻은 결론을 실행으로 옮기려면 결국 GitHub에 무언가를 해야 한다 — PR을 머지하고, 이슈를 만들고, 워크플로를 다시 돌리고, 릴리스를 낸다. 지금 그 일은 터미널의 `gh`에서 일어나고, 웹 대시보드는 조사에서 끊긴다. **PR Search는 조사와 실행을 같은 화면에서 잇는다.**

### 3.2 두 개의 Plane

제품은 두 축으로 나뉘며, 이 경계는 아키텍처·인증·감사 전반에서 유지된다 (ADR-013).

| Plane | 성격 | 트리거 | GitHub 자격 증명 | 실패 시 영향 |
| --- | --- | --- | --- | --- |
| **Search / Data Plane** | 읽기 전용 파생 시스템. 웹훅 수집 → PostgreSQL → Elasticsearch | 시스템 자동 (웹훅·잡) | GitHub Data App (server-to-server, 최소 read) | 검색 저하. GitHub에는 영향 없음 |
| **GitHub Operations Plane** | 사용자가 명시적으로 요청한 GitHub 작업의 실행 | 사용자 명시 요청만 | GitHub Operations App (user-to-server, 위임) | GitHub 상태 변경. 되돌리기 어려울 수 있음 |

Operations Plane이 Search/Data Plane을 대체하지 않는다. 수집·보강·채번·색인은 계속 웹훅과 GitHub REST API로 수행한다. `gh`는 **사용자가 요청한 작업의 실행 어댑터**일 뿐 데이터 파이프라인의 입력원이 아니다.

## 4. 범위 정의

### 4.1 In Scope

1. GitHub Enterprise 웹훅 이벤트(`pull_request`, `pull_request_review`, `push`, `create`, `delete`, `release`)의 수신, 서명 검증, 멱등 처리, 원본 보관
2. GitHub API 및 저장소 미러를 이용한 커밋 목록·변경 파일·리뷰 보강
3. 정규화 문서의 Elasticsearch 업서트와 인덱스 수명 관리
4. (저장소, 대상 브랜치) 단위 머지 시퀀스 채번, 범위 조회, 앵커 정규화, 히스토리 재작성 감지
5. 커밋 SHA ↔ PR 양방향 해석, 축약 SHA 접두 검색, 구조화 질의 문법, 다차원 필터, 정렬, 커서 페이지네이션, 패싯 집계, 전문 검색
6. 관계 간선 파생: 포함, 선행/후행, 참조, 되돌림, 체리픽, 스택, 동시 변경
7. 그룹핑·시계열·백분위·분포 집계와 통계 대시보드
8. OIDC SSO 인증, GHE 저장소 권한 기반 강제 필터링, 권한 캐시, 감사 기록
9. 운영 콘솔: 파이프라인 상태, 백필, 조정 스캔, DLQ 재처리, 무중단 재색인, 시퀀스 정합성 점검, 저장소 등록 관리
10. 사내 `design-system`(Conductor) 기반 웹 대시보드 화면 (W-001~W-009, A-001~A-004)

**GitHub Operations Plane (CR-005 신규)**

11. 버전 고정된 `gh` CLI의 capability manifest 구축과 유지 — command path, positional argument, flag, 제약, risk, 필요 권한을 기계 판독 가능한 형태로 보유하고 실제 `gh --help`와의 드리프트를 검출한다
12. capability manifest에서 생성되는 범용 command 폼(GenericCommandForm)과, 자주 쓰는 업무를 위한 전용 화면(W-010~W-023)
13. 격리된 실행기(`gh-executor`)에서의 `gh` 실행 — 고정 바이너리, `shell` 미사용, argv는 manifest에서 조립, 임시 workspace, 타임아웃·출력 상한·취소
14. 사용자를 대신하는 GitHub 작업 수행 — 별도 GitHub Operations App과 위임 사용자 액세스 토큰. 유효 권한은 App 권한과 사용자 권한의 **교집합**이다
15. 실행 위험도(R0~R3) 모델과 그에 따른 확인·승인 흐름, 실행 직전 대상 상태 재확인
16. 실행 이력·감사·재현: 실행 argv(비밀 마스킹), gh 버전, manifest 버전, 결과, 아티팩트
17. 등록된 capability만 조합하는 다단계 Recipe(W-023)와 저장된 명령
18. `gh api` 탐색기(W-020) — REST/GraphQL 요청을 command UI와 동일한 신원·권한·위험·감사 정책 아래 수행
19. PR·Issue·Discussion·Repository·Actions·Release·Project·Codespace·Label·Ruleset·Secret/Variable/Key·Search·Org·Status·Attestation·Gist 등 `gh` core 영역의 작업 (개별 action의 허용 여부는 실행 정책이 별도로 통제한다)

### 4.3 Out of Scope

CR-005로 재분류된 항목이 있다. 아래 표는 재분류 후의 최종 제외 목록이다.

| 제외 항목 | 사유 |
| --- | --- |
| **임의 shell 실행기** | 어떤 형태로도 제공하지 않는다. 사용자 입력 문자열을 명령으로 실행하는 경로(`bash -c`, `sh -c`, `eval`, `shell: true`)를 두지 않는다. `gh`는 고정 바이너리 + manifest에서 조립한 argv로만 실행한다 |
| **`gh alias --shell` 등가 기능** | 위와 같은 이유. 사용자 편의는 등록된 capability만 조합하는 Recipe(FR-GH-005)로 대체한다 |
| **Search/Data Plane의 `gh` 전환** | 수집·보강·채번·색인은 계속 웹훅과 GitHub REST API로 수행한다. `gh`는 사용자 요청 실행 어댑터이지 파이프라인 입력원이 아니다 (ADR-013) |
| **설치 토큰으로 사용자 권한 승격** | Operations App 설치 권한이 사용자 개인 권한보다 넓더라도 그 차이를 사용자에게 부여하지 않는다. 유효 권한은 항상 두 권한의 교집합이다 (FR-GH-008) |
| diff 본문(패치 텍스트) 저장과 코드 내용 검색 | 저장 용량과 소스 유출 위험. 변경 경로와 라인 수만 저장한다. 코드 검색은 GHE 기능을 사용한다 |
| 빌드·테스트 실행 로직의 자체 구현과 자동 이분 탐색 수행 | CI 시스템의 역할이다. 이 시스템은 후보 구간과 다음 검사 지점을 제시하고, 실행은 GitHub Actions 작업(FR-GH-004)으로 위임한다 |
| Perforce Changelist 히스토리 마이그레이션 | 전환 이전 데이터는 Perforce 서버에서 조회한다 |
| 개인 단위 생산성 순위표 | 인사 평가 오남용 위험. 집계는 팀·저장소 단위까지만 제공한다 |
| 저장소 간 통합 단일 시퀀스 | 저장소 사이에는 인과 순서가 없어 번호가 "이 이후는 안전하다"는 의미를 만들지 못한다 |
| 모바일 전용 애플리케이션 | 데스크톱 브라우저 반응형 레이아웃으로 대응한다 |
| 자연어 질의 → 검색 변환, 자연어 → `gh` 명령 변환 | 결과 재현성과 감사 추적 요구(NFR-006, NFR-012)와 충돌한다. 실행되는 argv는 항상 사용자가 구성한 값에서 결정론적으로 나온다 |
| 저장소 간 실시간 알림·구독 | 1차 범위 밖. 저장된 검색(FR-SRCH-010)까지만 제공한다 |
| GitHub 외 SCM·이슈 트래커 연동 | 대상은 사내 GitHub Enterprise 하나다 |

**CR-005에서 In Scope로 재분류된 항목** (이전 판의 제외 사유는 더 이상 유효하지 않다)

| 이전 제외 항목 | 새 분류 | 근거 |
| --- | --- | --- |
| GHE 쓰기 행위(PR 생성/리뷰/머지/코멘트) | In Scope | FR-GH-002, FR-GH-004. 다만 위험도별 확인·승인(FR-GH-009)과 감사(FR-GH-012)를 반드시 거친다 |
| Issue/Project/Discussion 도메인 | In Scope | FR-GH-004. 검색 색인 대상이 아니라 **작업 대상**으로 편입된다. 참조 관계에서 대상 ID 문자열로만 다루던 기존 처리(FR-REL-003)는 그대로 유지한다 |

재분류는 "제품이 그 기능을 다룬다"는 뜻이고, 개별 action의 허용 여부는 별개다. 제품 범위에 있는 capability라도 실행 정책(A-005)에서 `policy_blocked`이 될 수 있다.

## 5. 가정과 제약

### 5.1 기본 가정

1. 사내 PR 정책은 Squash & Merge 단일 정책이며, 머지된 PR 1건은 대상 브랜치에 커밋 1개를 만든다. Merge commit 및 Rebase merge 정책 저장소가 발견되면 DEV로 등록한다.
2. 보호 브랜치 정책으로 대상 브랜치(주로 `main`)의 강제 푸시는 예외 상황이며 상시 발생하지 않는다.
3. GitHub Enterprise 웹훅은 조직 단위로 이미 구성되어 있고, PR Search가 신규 엔드포인트를 등록할 수 있다.
4. GitHub API 접근용 App 또는 서비스 계정 토큰을 발급받을 수 있다.
5. 사내 OIDC IdP가 존재하고 그룹 클레임을 제공한다.
6. 대상 브랜치에 PR을 거치지 않은 직접 푸시 커밋이 존재할 수 있다. 이 커밋도 머지 시퀀스를 받되 소속 PR은 없음으로 표시한다.

### 5.2 기술 제약

1. 구현 언어는 프런트엔드·백엔드·배치 전 계층 TypeScript로 통일한다.
2. 검색·집계는 Elasticsearch 8.x를 단일 질의 대상으로 사용한다.
3. 원본 이벤트와 시퀀스 상태의 시스템 오브 레코드는 PostgreSQL이며, Elasticsearch 인덱스는 PostgreSQL로부터 전량 재구성 가능해야 한다.
4. GitHub API는 시간당 요청 상한이 있으므로 보강 처리는 상한 인지형 스케줄링을 사용한다.
5. 웹 대시보드는 사내 `design-system`(Conductor) 패키지만 UI 프리미티브로 사용하고, 별도 UI 라이브러리를 도입하지 않는다.
6. 배포 대상은 사내 Kubernetes 클러스터이며 인터넷에 노출하지 않는다.

### 5.3 보안/운영 제약

1. 웹훅 요청은 HMAC-SHA256 서명 검증을 통과해야만 처리한다.
2. 사용자는 GHE에서 read 이상 권한을 가진 저장소의 데이터만 조회할 수 있다. 권한 미확인 상태의 기본값은 거부다.
3. 저장 데이터에 소스 코드 본문을 포함하지 않는다.
4. GitHub 토큰과 웹훅 시크릿은 클러스터 시크릿 저장소에서만 읽고 로그에 남기지 않는다.
5. 조회·내보내기·관리 액션은 감사 기록 대상이다.

## 6. 사용자와 권한 모델

| 사용자 유형 | 권한 | 주요 목표 |
| --- | --- | --- |
| 개발자 (`developer`) | 접근 범위 내 조회, 저장된 검색 생성 | 장애 원인 PR 특정, 선행·후행 조사 |
| 릴리스 매니저 (`release_manager`) | 개발자 권한 + 안전 구간 표식 쓰기 | 배포 구간 확정, 릴리스 비교 |
| 조직 관리자 (`manager`) | 소속 조직 범위의 조회·집계 | 팀·저장소 단위 지표 확인 |
| QA (`qa`) | 개발자와 동일 | 회귀 원인 구간 축소 |
| 플랫폼 운영자 (`operator`) | 전체 조회 + 운영 콘솔 쓰기(백필, 재색인, DLQ 재처리, 저장소 등록) | 파이프라인 운영 |
| 보안 담당자 (`security_officer`) | 감사 로그 조회 | 접근 이력 감사 |

권한 판정 규칙:

- 접근 범위(`access_scope`)는 사용자가 GHE에서 read 이상 권한을 가진 저장소 ID 집합이다.
- 모든 검색·집계 질의에는 접근 범위 조건이 서버 측에서 강제 결합된다. 클라이언트가 보낸 필터로 이 조건을 우회할 수 없다.
- `operator`와 `security_officer` 역할은 접근 범위와 무관하게 각각 운영 데이터와 감사 데이터를 조회할 수 있으나, PR·커밋 본문 조회에는 동일한 접근 범위 규칙이 적용된다.

## 7. 대표 사용자 시나리오

### SCN-001 장애 커밋에서 원인 PR 역추적

- 목표: 축약 커밋 SHA 하나로 원인 PR과 작성자를 특정한다.
- 시작 조건: 사용자에게 7자 축약 SHA 문자열만 있다.
- 기본 흐름: 통합 검색 입력 → 접두 일치 해석 → 커밋 상세 진입 → 소속 PR·작성자·리뷰어·머지 시퀀스 확인.
- 예외 흐름: 후보 2건 이상이면 모호성 목록 제시. 0건이면 미수집 저장소 안내.
- 관련 요구사항: FR-SRCH-001, FR-SRCH-002, FR-SRCH-004, FR-REL-002

### SCN-002 배포 구간 조사

- 목표: 두 릴리스 사이에 들어간 PR 목록을 확정한다.
- 시작 조건: 정상 릴리스 태그와 장애 릴리스 태그를 알고 있다.
- 기본 흐름: 범위 조사 화면에서 두 앵커 지정 → 시퀀스 값으로 정규화 → 구간 PR 목록을 머지 순서로 조회 → 패싯으로 후보 축소.
- 예외 흐름: 두 앵커가 다른 시퀀스 공간에 속하면 비교를 거부한다.
- 관련 요구사항: FR-SEQ-002, FR-SEQ-003, FR-SEQ-004, FR-SRCH-006, FR-SRCH-009

### SCN-003 선행·후행 확인과 후보 좁히기

- 목표: 의심 PR 주변을 확인하고 조사 구간을 절반씩 줄인다.
- 시작 조건: 의심 PR 1건이 특정되어 있다.
- 기본 흐름: PR 상세에서 선행 10건·후행 10건 확인 → 이분 탐색 보조에서 good/bad 표시 → 후보 구간 축소.
- 예외 흐름: 대상 PR이 미머지면 시퀀스가 없으므로 선행·후행 탐색을 비활성화한다.
- 관련 요구사항: FR-REL-001, FR-REL-004, FR-SEQ-007

### SCN-004 이 PR이 어느 릴리스에 들어갔는가

- 목표: 특정 PR의 배포 시점을 확인한다.
- 시작 조건: PR 번호를 알고 있다.
- 기본 흐름: PR 상세의 포함 릴리스 섹션 확인 → 해당 머지 커밋을 포함하는 릴리스 목록과 시각 확인.
- 예외 흐름: 어떤 릴리스에도 포함되지 않았으면 미배포 상태와 대기 PR 수를 표시한다.
- 관련 요구사항: FR-REL-002, FR-SEQ-004

### SCN-005 조직 지표 확인

- 목표: 기간·조직 단위 지표를 확인하고 근거 목록으로 이동한다.
- 시작 조건: 관리자가 월간 리뷰를 준비한다.
- 기본 흐름: 통계 대시보드에서 기간·조직 지정 → 그룹 집계·시계열·백분위 확인 → 특정 그룹 선택 시 동일 조건 검색 결과로 이동.
- 예외 흐름: 집계 대상 문서 수가 상한을 넘으면 근사값임을 표시한다.
- 관련 요구사항: FR-STAT-001, FR-STAT-002, FR-STAT-003, FR-STAT-006

### SCN-006 수집 지연 대응

- 목표: 검색 결과 누락 원인을 찾아 복구한다.
- 시작 조건: 운영자가 데이터 누락 문의를 받았다.
- 기본 흐름: 운영 콘솔에서 지연·DLQ 확인 → 원인 이벤트 조회 → 재처리.
- 예외 흐름: 웹훅 자체 누락이면 조정 스캔을 실행한다. 재처리 재실패 시 보류 상태 유지와 알림.
- 관련 요구사항: FR-ING-007, FR-ING-011, FR-ADMIN-001, FR-ADMIN-002

### SCN-007 되돌림·체리픽 추적

- 목표: 핫픽스가 릴리스 브랜치에 반영됐는지 확인한다.
- 시작 조건: 원본 PR을 알고 있다.
- 기본 흐름: PR 상세 관계 섹션에서 체리픽 대응 커밋과 대상 브랜치 확인.
- 예외 흐름: 자동 탐지 실패 시 신뢰도 표기와 함께 트레일러 기반 후보만 제시한다.
- 관련 요구사항: FR-REL-004, FR-REL-005

## 8. 기능 실현 방식 분류

- Type A: 기존 API 또는 설정으로 구현 가능
- Type B: 서버/백엔드 실행 계층 필요
- Type C: UX 재설계 필요
- Type D: 정책상 제외 또는 후순위

이 제품의 승인 기능은 전부 Type B다. 수집·정규화·시퀀스 채번·관계 파생이 모두 서버 실행 계층을 요구한다.

## 9. 기능 요구사항

작성 규칙 요약:

- 요구사항 문장은 EARS 패턴 중 하나를 따른다: 상시(시스템은 항상 X한다) / 이벤트(T가 발생하면 X한다) / 상태(S인 동안 X한다) / 예외(오류 E가 발생하면 X한다) / 선택(기능 F가 활성화된 경우 X한다).
- 하나의 FR에는 하나의 검증 가능한 행위만 담는다.
- 수치 없는 형용사/부사는 사용하지 않는다. 수용 기준(AC)은 pass/fail 판정이 가능해야 한다.
- 검증 방법: test(자동 테스트) / demo(시연) / inspection(검사) / analysis(분석) 중 하나.

### 9.8 FR-GH GitHub Operations Plane

CR-005로 추가된 요구사항 그룹이다. 이 그룹은 사용자가 명시적으로 요청한 GitHub 작업의 구성과 실행을 다룬다. 수집·검색 파이프라인(FR-ING, FR-SRCH)과는 신원·권한·감사 경계가 분리된다 (ADR-013).

기준 도구는 버전이 고정된 `gh` CLI다. 실측 기준값은 gh 2.97.0(2026-07-31)이며, command node 228개 전부에 `gh <path> --help`를 실행해 측정했다 (CR-008에서 재실측).

| 차원 | gh 2.97.0 실측값 |
| --- | --- |
| command node | 228 (실행 가능 leaf 196, 그룹 32) |
| alias 전용 노드 | 1 (`gh co` → `gh pr checkout`) |
| alias를 가진 command | 44 |
| positional placeholder | 230 |
| command 고유 flag | 1,034 |
| inherited/global flag 출현 | 312 (고유 4종: `--codespace`, `--help`, `--repo`, `--repo-owner`) |
| short alias를 가진 flag | 625 |
| 반복 가능 flag | 37 |
| `--json` 지원 command | 41 |
| `--json` 필드 정의 | 707 |

이전 판은 positional placeholder를 261개로 적었으나 실측은 230개다 (DEV-011, CR-008에서 정정). 이 수치는 고정값이 아니라 고정된 버전에서 측정한 값이며, 버전이 바뀌면 manifest와 함께 갱신된다.

**parity의 차원 (CR-008).** "모든 기능과 유효한 조합을 웹에서 표현한다"는 요구는 command path와 flag 목록만으로 충족되지 않는다. capability manifest는 아래 28개 차원을 모두 분류해야 한다.

| # | 차원 | # | 차원 |
| --- | --- | --- | --- |
| 1 | command path | 15 | 실행에 영향을 주는 환경 컨텍스트 |
| 2 | command alias | 16 | interactive/TTY 요구 |
| 3 | positional argument | 17 | editor/browser 요구 |
| 4 | command 고유 flag | 18 | 출력 형식 |
| 5 | inherited/global flag | 19 | `--json` 필드 |
| 6 | short/long flag alias | 20 | `--jq` |
| 7 | 반복 가능 flag | 21 | `--template` |
| 8 | stdin 입력 | 22 | 페이지네이션/slurp |
| 9 | 파일 입출력 | 23 | REST/GraphQL 모드 |
| 10 | 현재 저장소 컨텍스트 | 24 | 대상 GHES 버전 |
| 11 | 호스트 컨텍스트 | 25 | 사용자 권한 |
| 12 | 브랜치/ref 컨텍스트 | 26 | Operations App 권한 |
| 13 | 로컬 workspace 필요 여부 | 27 | PR Search 정책 |
| 14 | gh 구성(config) | 28 | 위험도 |

토큰·비밀 값 자체는 이 차원에 포함되지 않는다. `GH_ENTERPRISE_TOKEN` 같은 값은 실행기가 안전하게 주입하며 UI에 나타나지 않는다 (NFR-010).

**조합 parity (CR-009).** 위 28개 차원은 *한 command*의 유효 조합을 다룬다. 그러나 실제 업무는 명령 하나로 끝나지 않는다 — 검색 결과에서 PR 하나를 골라 체크를 보고, 릴리스에서 받은 파일을 다음 명령에 넣는다. 명령마다 특수 코드를 넣지 않고 이것을 일반화하려면 **출력에도 계약이 필요하다.**

기존 Recipe(FR-GH-005)는 이전 단계의 **JSON 출력** 바인딩까지만 표현한다. 그런데 gh 명령의 출력이 전부 JSON은 아니다.

| 실제 상황 | 기존 표현으로 안 되는 이유 |
| --- | --- |
| 명령 A가 저장소 URL을 반환 → 명령 B가 저장소 입력을 요구 | URL은 JSON 필드가 아니다 |
| `gh release download`가 파일 생성 → 다음 명령이 파일 입력 필요 | 파일은 JSON 필드가 아니고, 실행기 경로를 넘겨서도 안 된다 |
| `gh search prs`가 PR 집합 반환 → `gh pr checks`는 PR 하나 필요 | 집합에서 하나를 고르는 의미가 표현되지 않는다 |
| `gh run rerun`은 workflow run 참조 필요 | `owner/repo#123` 문자열을 매번 재파싱하게 된다 |

그래서 다음 다섯 가지를 capability manifest에 추가한다.

**1. `GhResultContract` — 결과 계약.** 각 capability는 입력 계약과 함께 결과 계약을 가진다.

| 필드 | 내용 |
| --- | --- |
| `kind` | `json`, `resource`, `resource_list`, `url`, `artifact`, `text`, `stream`, `exit_status` |
| `schema` | 구조화 출력의 스키마 |
| `resourceType` | 결과가 가리키는 자원 종류 |
| `bindable` | 다음 단계의 입력으로 이을 수 있는가 |
| `sensitivity` | `public`, `internal`, `sensitive`, `secret` |
| `adapters` | 구조화 수단 (아래 참조) |

**2. 결과 sensitivity — `secret` 결과는 다르게 다룬다.** `gh auth token`, 비밀 조회, 자격 증명 자료의 결과를 일반 결과와 같이 취급하지 않는다. `secret`으로 분류된 결과는 화면 표시, 실행 이력 저장, Recipe 바인딩, 감사 본문 저장, 다음 명령 stdin 자동 전달을 **모두 금지**한다.

**capability가 UI에 존재하는 것과 비밀 값을 노출하는 것은 다른 문제다.** capability는 목록에 보이고 실행될 수 있으면서도 그 출력은 non-bindable·policy-blocked일 수 있다. 숨기는 것이 아니라 흐르지 못하게 하는 것이다.

**3. `GhResourceRef` — 공통 자원 참조.** 명령 사이에서 `owner/repo#123` 같은 문자열을 다시 파싱하지 않는다. `{ host, kind, repository, id, number, ref }` 구조로 넘긴다. `kind`는 `repository`, `pull_request`, `issue`, `discussion`, `workflow`, `workflow_run`, `release`, `project`, `codespace`, `artifact`, `gist`, `user`, `team`, `branch`, `commit`이다.

**4. typed 입출력 port.** capability는 바인딩 가능한 입력·출력 port를 가진다. `gh search prs`의 출력은 `PullRequestRef[]`, `gh pr checks`의 입력은 `PullRequestRef`이고 출력은 `CheckRunRef[]`, `gh run rerun`의 입력은 `WorkflowRunRef`다. **어떤 명령 뒤에 어떤 명령을 이을 수 있는지는 타입으로 계산한다** — 이름 문자열이 같아서 잇는 것이 아니다.

**5. `GhCapabilityGraph`.** manifest에서 node=capability, edge=출력 port → 호환 입력 port 인 그래프를 자동으로 계산한다. W-023이 다음 단계를 제안할 때 전체 명령을 무작정 나열하지 않고 현재 출력과 호환되는 것을 먼저 보여준다. 전체 검색은 계속 되지만, 호환되지 않는 연결은 저장 전에 사유와 함께 거부한다.

**`--json`이 없는 명령의 result adapter.** 모든 명령이 `--json`을 지원하지는 않는다. 각 결과를 아래로 분류한다.

| adapter | 의미 |
| --- | --- |
| `native_json` | 명령 자체가 `--json`을 지원 |
| `gh_api_structured` | 자체 `--json`은 없지만 같은 의미를 `gh api`로 구조화할 수 있다 (명령 의미가 달라지면 쓰지 않는다) |
| `resource_url` | 결과가 자원 URL |
| `artifact` | 결과가 파일 |
| `opaque_text` | 구조를 신뢰할 수 없는 텍스트 |
| `stream` | 스트리밍 출력 |
| `exit_status` | 종료 코드만 의미가 있다 |
| `secret_non_bindable` | 비밀 자료 |

**출력 텍스트를 깨지기 쉬운 정규식으로 무조건 파싱하지 않는다.** `opaque_text`는 실행하고 화면에 보여줄 수 있지만 typed 바인딩의 source가 될 수 없다고 분류한다. 목록에서 숨기지 않는다.

**composability 상태.** 모든 capability는 아래 중 하나를 가지며 `unknown`은 금지한다.

`fully_bindable`, `partially_bindable`, `terminal_result`, `artifact_result`, `opaque_result`, `secret_non_bindable`, `policy_blocked`, `unsupported_by_host`

## 11. 데이터 및 추적성 요구사항

1. 모든 검색 문서는 원본 이벤트로부터 재구성 가능해야 한다. 검색 인덱스는 파생 뷰이며 시스템 오브 레코드가 아니다.
2. 모든 검색 문서는 마지막으로 반영한 이벤트의 전달 식별자와 반영 시각을 보유한다.
3. 머지 시퀀스 값은 `(저장소, 대상 브랜치, 에폭)`과 함께 저장되어야 하며, 에폭 없이 인용된 시퀀스 값은 유효하지 않은 것으로 취급한다.
4. 모든 관계 간선은 유형, 방향, 신뢰도, 근거 문자열을 보유한다. 근거 없는 간선은 저장하지 않는다.
5. 커밋 문서는 SHA를 문서 ID의 일부로 사용해 저장소 간 SHA 충돌 없이 식별되어야 한다.
6. 문서 삭제는 저장소 등록 해제 시에도 수행하지 않는다. 상태 플래그로만 표시한다.
7. 소스 코드 본문, 패치 텍스트, 파일 내용은 저장하지 않는다. 변경 경로 문자열과 라인 수만 저장한다.
8. 모든 GitHub 작업 실행은 감사 기록 없이 시작되지 않는다. 감사 기록 실패는 쓰기 실행의 차단 사유다 (FR-GH-012).
9. 실행 기록은 그 실행을 재현할 수 있을 만큼의 정보를 보유한다 — capability ID, 구성 값, gh 버전, manifest 버전과 해시. 단 비밀 값은 보유하지 않는다.
10. GitHub 액세스 토큰과 사용자가 입력한 비밀 값은 어떤 영속 저장소에도 평문으로 기록되지 않는다. 데이터베이스에는 비밀 저장소 참조와 메타데이터만 저장한다 (FR-GH-008).
11. capability manifest는 버전과 내용 해시를 가지며, 실행 기록은 자신이 사용한 manifest 버전을 참조한다. 과거 실행의 argv 해석은 그 시점 manifest로 가능해야 한다.

### NFR-009 gh capability 커버리지

CR-005 신규. 이 지표는 릴리스 게이트다 — 하나라도 미달이면 GitHub Operations Plane 릴리스를 승인하지 않는다.

**지원하지 않는 것은 실패가 아니다.** 아래 상태로 명확히 분류되면 커버리지에 포함된다.

`supported`, `web_equivalent`, `sandbox_terminal`, `unsupported_by_host`, `policy_blocked`, `terminal_only`, `requires_extension`, `requires_local_workspace`

**목록에서 사라지는 것은 분류가 아니다.** 숨겨진 capability는 미분류로 집계하고 게이트를 실패시킨다.

"모든 조합 지원"은 유효한 모든 조합을 스키마가 표현할 수 있다는 뜻이지, 모든 조합을 CI에서 실제 호출한다는 뜻이 아니다 — 데카르트 곱을 전부 돌리지 않는다. 조합 검증은 다음으로 수행한다 (CR-008).

| 검증 | 내용 |
| --- | --- |
| 인벤토리 커버리지 | 실제 gh 바이너리에서 뽑은 항목이 전부 분류되었는가 |
| 스키마 검증 | manifest가 스키마를 만족하는가 |
| 제약 속성 시험 | 스키마가 유효하다고 판단한 조합을 argv 빌더가 표현할 수 있는가, 무효 조합을 서버가 거부하는가, UI와 서버 판정이 같은가, argv 생성이 결정론적인가 |
| 유효/무효 조합 생성기 | 제약 모델에서 조합을 생성해 양쪽을 검사 |
| 페어와이즈 조합 시험 | flag 쌍 단위 상호작용 |
| 핵심 워크플로 시나리오 | 실제 업무 흐름 |
| golden argv 시험 | 고정 invocation → 고정 argv |

속성 시험이 반드시 포함해야 하는 성질: 사용자 입력이 command path 자체를 바꿀 수 없다, shell 메타문자가 shell 의미를 갖지 않는다, `shell: true` 경로가 0건이다.

**gh 출력은 신뢰할 수 없는 입력이다 (CR-008, ADR-018).** 실행기의 stdout·stderr와 GitHub에서 내려온 모든 텍스트(제목, 본문, 라벨, 브랜치 이름, 파일 경로, 사용자 이름)는 외부 입력이다. gh 2.97.0 자신도 외부 입력이 섞인 터미널 escape 처리 문제를 보안 수정한 이력이 있으므로, PR Search는 gh가 출력을 안전하게 만들어 준다고 가정하지 않는다.

모든 출력은 `SafeGhOutput` 경계를 통과한다.

| 처리 | 내용 |
| --- | --- |
| ANSI CSI 시퀀스 | 무해화 |
| OSC 시퀀스 | 무해화 (터미널 제목·클립보드·하이퍼링크 주입 차단) |
| 기타 터미널 제어 문자 | 제거 또는 escape |
| 원시 HTML | 실행 금지 |
| Markdown | 안전 렌더러만 사용 |
| 잘못된 UTF-8 | 대체 문자로 치환 |
| 출력 크기 | 바이트 상한 적용 후 절단 표시 |
| 바이너리 출력 | 탐지해 텍스트로 렌더링하지 않음 |
| 스트리밍 경계 | 청크 경계에서 escape 시퀀스가 잘려도 안전하게 처리 |
