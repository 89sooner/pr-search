# PR Search 와이어프레임 사양서

> 상태: review | 버전: v0.13 | 갱신일: 2026-08-30

## 0. 문서 위치와 책임

이 문서는 화면별 목적, 진입 경로, 레이아웃, 섹션, 컴포넌트, 상태, 이벤트, 권한/정책을 정의한다. 화면 ID는 `pr_search_product_ia.md`에서 선언한 것만 사용한다. 상태 이름은 `pr_search_screen_state_matrix.md`의 공통 상태 분류를 따른다. 컴포넌트 ID는 `pr_search_ui_component_spec.md`에서 정의한다.

## 1. 공통 화면 사양 형식

각 화면은 다음 순서를 따른다.

- 화면 목적
- 진입 경로
- 레이아웃 구조
- 섹션 정의
- 주요 컴포넌트
- 상태 정의
- 이벤트 정의
- 권한/정책
- 구현 메모

## 2. 전역 셸

모든 화면은 Conductor `AppShell`로 감싼다.

- `topBar`: `C-001 AppTopBar` — 제품명, `C-010 OmniSearchInput`, 시퀀스 공간 선택기, 사용자 메뉴
- `nav`: `C-002 LeftNavPanel` — Conductor `NavList` 기반
- `skipLinkLabel`: "본문으로 건너뛰기"
- `mainId`: `main-content`

## W-001 통합 검색

### 화면 목적

사용자가 가진 식별자 또는 조건으로 PR·커밋·릴리스를 찾고, 결과를 필터·정렬·집계한다. 이 제품의 기본 진입 화면이다.

### 진입 경로

- 애플리케이션 루트 `/`
- TopBar 옴니 검색에서 후보 2건 이상 또는 자유 텍스트 해석
- W-006 그룹·구간 클릭 (질의 문자열 전달)
- W-008 저장된 검색 실행
- 딥링크 `/search?q=<질의>&sort=<키>&cursor=<커서>&seq_epoch=<에폭>`. **`seq_epoch`은 `seq:` 질의에서만 뜻이 있다** — 그 조건이 어느 히스토리 세대의 서수를 가리켰는지를 URL이 보존한다 (ADR-007 규칙 5, CR-051). 질의에 `seq:`가 없으면 이 파라미터를 두지 않는다
- 상세 화면에서 뒤로가기: 상세로 이동할 때 원본 입력을 **`from_q`**로 남긴다 (CR-019, DEV-078). `q`를 쓰지 않는 이유는 상세 URL에 `q`가 있으면 그 화면이 검색 결과인 것처럼 읽히기 때문이다

### 레이아웃 구조

```text
┌─────────────────────────────────────────────────────────────────────┐

├───────────────┬─────────────────────────────────────────────────────┤
│ 필터 레일     │ [탭: 결과 | 집계]                                    │

│               │ │ 결과 요약: N건 · 정렬 [머지 시퀀스 ▾]           │ │
│ 저장소   ▾    │ ├─────────────────────────────────────────────────┤ │
│ 작성자   ▾    │ │ [seq] [유형] 제목            작성자 머지시각 규모│ │

### 섹션 정의

| 섹션 | 내용 | 관련 FR |
| --- | --- | --- |
| `W-001-QUERY` 질의 입력 바 | 구조화 질의 문자열 입력, 파싱된 토큰 칩 표시, 오류 구간 강조. **`seq:` 범위 조건은 `repo:`·`base:`를 하나씩 함께 요구한다** (FR-SRCH-005 AC-7, CR-051) — 없거나 여럿이면 서버가 실행하지 않고 거절하며, 화면은 무엇이 부족한지를 입력 바 아래에 적는다. **질의를 자동으로 고쳐 주지 않는다**: 어느 저장소를 뜻했는지는 사용자만 안다 | FR-SRCH-005 |
| `W-001-FACETS` 필터 레일 | **패싯 축 여섯**(저장소·작성자·팀·라벨·대상 브랜치·PR 상태), 각 상위 20개 값과 건수. 기간·시퀀스는 **필터 입력이지 패싯이 아니다** — 연속 값이라 분포를 상위 20으로 셀 수 없고 SRS AC-1도 여섯만 정한다 (CR-043). 레일 상태 넷을 구분한다: 세지 않음 · 준비됨 · 예산 초과 생략 · 계산 실패 | FR-SRCH-006, FR-SRCH-009 |
| `W-001-SUMMARY` 결과 요약 | 총 건수, 적용 필터 수, 정렬 선택기, 근사 집계 표기 | FR-SRCH-007 |
| `W-001-RESULTS` 결과 테이블 | 시퀀스, 유형(PR/커밋), 제목(강조 포함), 작성자, 머지 시각, 변경 규모, **관계 배지(`C-015`)**. 배지는 **WP-031이 붙인다** — WP-029까지 `link_summary`가 비어 있어 빈 열을 미리 두면 "관계 없음"으로 읽혔고(CR-019, DEV-081), WP-030이 값을 채우면서 도달 가능해졌다 (CR-042, DEV-262). **배지는 목록 응답의 비정규화 `link_summary`로만 그린다** — 행마다 관계를 조회하지 않는다 (ADR-009, DEV-264). `link_summary`가 **없는 행**은 배지 영역을 그리지 않는다: "요약이 아직 없다"와 "관계가 없다"는 다른 사실이다 | FR-SRCH-006, FR-SRCH-011, FR-REL-004, FR-REL-005 |
| `W-001-PAGER` 페이저 | 커서 기반 더 보기. 페이지 번호 UI를 두지 않는다(WP-016이 이미 세웠다). 이어 보기는 패싯을 다시 요청하지 않으며, 커서가 거절되면(`CURSOR_QUERY_MISMATCH` / `CURSOR_INVALID`) **사유를 구분해 알리고** 현재 조건의 첫 페이지로 되돌아간다 — 자동 재시도 루프를 만들지 않는다 (CR-043) | FR-SRCH-008 |
| `W-001-SEQCTX` 시퀀스 인용 배너 | `seq:` 질의일 때만 나타난다. 현재 조회가 딛고 선 시퀀스 공간과 에폭을 적고, **요청한 에폭이 현재와 다르면 결과 대신 이 배너만 그린다** — 목록·요약·패싯을 그리지 않는다 (FR-SEQ-005 AC-4, CR-051). 빈 결과로 그리면 "그 구간이 비었다"로 읽히기 때문이다. 배너는 요청한 에폭과 현재 에폭을 함께 보이고 **「현재 에폭으로 다시 조회」 하나만** 액션으로 제공한다 — 자동으로 옮기지 않는다. 공간 상태가 `stale`·`reassigning`이면 그 사실도 값과 함께 적되 조회는 막지 않는다 | FR-SEQ-005, FR-SRCH-005 |
| `W-001-AGG` 집계 탭 | 현재 질의 조건 위의 그룹 집계 결과 | FR-STAT-006 |
| `W-001-AMBIG` 모호성 목록 | 옴니 해석 후보가 2건 이상일 때 표시하는 후보 카드 목록 | FR-SRCH-001, FR-SRCH-004 |
| `W-001-ACTIONS` 액션 | 저장된 검색으로 저장, 결과 내보내기. **저장 대화상자는 현재 URL의 정본 질의 문자열을 그대로 담는다** — 질의를 다시 조립하지 않는다(구현 메모의 "질의 문자열이 URL의 단일 진실"과 같은 규율). 받는 것은 이름과 공개 범위이며, 공개 범위가 `team`이면 **대상 팀 하나를 선택기로 고른다**. 선택지는 현재 사용자가 구성원인 팀뿐이고 같은 slug이 여러 조직에 있으면 조직으로 구분해 표시하되 값은 언제나 `team_id`다. 소속 팀이 없으면 `team` 선택지를 비활성화하고 사유를 적는다. 정렬·패싯 선택·커서는 저장하지 않는다 (CR-049) | FR-SRCH-010, FR-SRCH-012 |

### 권한/정책

- 인증 필요. 미인증 요청은 OIDC로 리다이렉트한다 (FR-AUTH-001).
- 결과는 서버가 접근 범위를 강제 결합한 것만 표시한다. 클라이언트는 접근 범위 필터를 조작할 수 없다 (FR-AUTH-002).
- 내보내기는 감사 기록 대상이며 실행 전 대상 건수를 확인 다이얼로그로 표시한다 (FR-SRCH-012, FR-AUTH-004).
- 저장된 검색을 팀에 공유하는 것은 **그 검색의 이름과 질의 문자열을 대상 팀에 보이게 하는 일**이며, 질의에 적힌 저장소에 대한 접근 권한을 주지 않는다. 공유받은 사람이 그것을 실행해도 결과는 언제나 실행한 사람의 접근 범위로 계산된다 (FR-SRCH-010 AC-3, THR-012, CR-049).

### 구현 메모

- 질의 문자열이 URL의 단일 진실이다. 필터 레일 조작은 질의 문자열을 갱신하고, 질의 문자열 변경이 조회를 유발한다. 두 방향의 상태를 따로 두지 않는다.
- **`seq:` 질의의 첫 조회는 URL을 완성한다** (CR-051). 요청에 `seq_epoch`이 없으면 서버가 현재 에폭으로 바인딩해 응답에 실어 주고, 화면은 그 값을 URL에 `replace`로 기록한다 — `push`가 아니다. 에폭 고정은 새 조사 단계가 아니라 **지금 보고 있는 조회의 정본 주소를 완성하는 일**이며, 사용자가 곧바로 주소를 복사해도 에폭이 들어 있어야 한다. 컴포넌트 상태에만 두면 그 주소는 다른 세대를 가리키게 된다.
- **질의가 `seq:`를 잃으면 `seq_epoch`도 함께 지운다.** 뜻이 없는 파라미터를 남기면 다음 조회가 그것을 근거로 거절당한다.
- 목록 조회와 패싯 조회는 하나의 API 응답으로 받되, 레일은 **세 경우를 구분해 표시한다** (CR-019, DEV-076): `facets` 키가 **없으면** "아직 세지 않음"(WP-032 전), `facets_omitted: true`면 "이번 조회에서 생략", 있으면 분포. 어느 쪽이든 **조용히 비우지 않는다**.
- 시퀀스가 **아직 계산되지 않은 것**(WP-021 전, 값이 `null`)은 `not_computed`로 그린다. 미머지(`unassigned`)로 그리면 화면이 거짓을 말한다 (CR-019, DEV-077).
- 결과 행의 시퀀스 배지는 시퀀스 공간(저장소·브랜치)을 툴팁으로 표시한다. 서로 다른 공간의 시퀀스 값을 나란히 보여줄 때 비교 가능한 값으로 오인되지 않도록 공간이 다르면 배지 색조를 `neutral`로 낮춘다.
- 7자 미만 hex 입력은 서버 호출 없이 클라이언트에서 즉시 `error_prefix_too_short` 안내를 띄운다 (FR-SRCH-004 AC-2).

## W-002 PR 상세

### 화면 목적

PR 1건의 전체 맥락 — 커밋 집합, 시퀀스 위치, 선행·후행, 포함 릴리스, 관계 — 을 한 화면에서 확인하고 다음 조사 단계로 이동한다.

### 진입 경로

- 옴니 검색 해석 결과 (유형 `pull_request`)
- W-001 결과 행 클릭
- W-003 "소속 PR" 클릭
- W-004 범위 결과 행 클릭
- 딥링크 `/pr/:owner/:repo/:number`

### 레이아웃 구조

### 구현 메모

- 헤더·개요·커밋은 진입 시 함께 조회한다. 관계·동시 변경은 섹션 확장 시 조회한다 (IA 원칙 4, 점진적 공개).
- 미머지 PR은 `W-002-NEIGHBORS`를 비활성 상태로 렌더링하고 "머지 후 시퀀스가 부여됩니다"를 표시한다. 섹션 자체를 숨기지 않는다 — 숨기면 사용자가 기능 부재로 오인한다. **이때 조회를 보내지 않는다** (CR-031, DEV-164): PR 문서의 `state`로 이미 아는 사실이므로 409를 일부러 유발해 놓고 받아 내지 않는다. 머지됐으나 아직 채번되지 않은 PR은 **다른 문구**다 — "머지되지 않았다"는 사실 주장과 "아직 모른다"를 같이 그리지 않는다 (C-014의 규칙, DEV-077).
- **"범위로 확장"이 넘기는 앵커는 지금 보고 있는 이웃 창이다** (CR-031, DEV-167): 목록 첫 항목의 서수가 시작(제외), 마지막 항목의 서수가 끝(포함)이다. 화면이 본 것과 W-004가 조회할 것을 같게 한다 — 서수를 앵커로 넘기므로 새 앵커 유형을 만들지 않는다 (WP-026 미배포 링크와 같은 규칙).
- `epoch_stale` 상태에서는 헤더 아래에 Conductor `Banner`(tone `warning`)로 "시퀀스가 재채번되어 이전에 인용한 범위는 무효합니다"를 표시한다. **WP-021·022가 서면서 도달 가능해졌고, WP-027이 만든다** (CR-031, DEV-165 — DEV-087의 이월을 닫는다). 감지 경로는 W-004와 같다: PR 문서가 실어 온 `seq_epoch`와 선행·후행 응답의 현재 에폭을 비교하며, **자동 재조회는 하지 않는다** (QA-W002-16, FR-SEQ-005 AC-4).
- 관계 항목의 신뢰도는 `exact`/`derived`/`heuristic` 세 단계를 배지로 구분하고, `heuristic`은 근거 문자열을 항상 함께 표시한다.
- 딥링크의 `:number`는 **앞자리 0이 없는 양의 정수**만 받는다. 그 밖(`abc`, `0`, `007`, `-1`, 소수)은 조회하지 않고 `not_found`를 보인다 — `007`을 받아 주면 URL과 다른 PR(`#7`)을 그리게 되고, 조사 결과를 URL로 인용하는 제품에서 그것은 치명적이다. **문구는 접근 범위 밖과 같아야 한다** — 다르게 말하면 존재 여부를 가르는 신호가 된다 (FR-AUTH-002 AC-4).

- W-002와 동일한 접근 범위 규칙을 적용한다.

### 구현 메모

- `no_sequence` 상태는 PR head 브랜치의 원본 커밋에서 정상적으로 발생한다. 오류가 아니라 "이 커밋은 대상 브랜치에 직접 존재하지 않고 머지 커밋 X로 반영되었습니다"라는 설명과 머지 커밋 링크를 제공한다.
- **`no_sequence`는 시퀀스 값이 아니라 역할로 판정한다** (CR-021, DEV-092). `merge_seq`가 WP-021까지 모든 커밋에서 `null`이라 값만 보면 머지 커밋까지 "체인 밖"이 된다. `role === 'source_commit'`은 **정의상** first-parent 체인 밖이고(squash merge에서 원본 커밋은 브랜치에 직접 착지하지 않는다), 이는 시퀀스 없이 지금 말할 수 있는 사실이다. `merge_commit`인데 `merge_seq`가 `null`인 것은 **미채번**이고 다른 문구를 쓴다.
- **머지 커밋 링크는 소속 PR의 `merge_commit_sha`로 만든다** — API-SRCH-002가 그 키를 싣는다 (CR-021, DEV-091). 미머지 PR이면 키가 없고, 그때는 링크 대신 PR로 가는 길만 준다.
- **`reason_code: 'no_pull_request'`를 "직접 푸시"라고 부르지 않는다** (CR-021, DEV-093). 그것은 "투영이 아직 PR 번호를 잇지 못했다"이고, 직접 푸시는 `role: 'direct_push'`다 — 후자는 WP-021 전까지 도달하지 않는다(DEV-061).
- SHA 표시는 기본 12자 축약, 클릭 시 전체 40자 툴팁, 복사 버튼은 항상 전체 40자를 복사한다. **복사 실패도 알린다** (CR-021, DEV-096).

### 구현 메모

- 릴리스 목록의 "직전 릴리스 대비 PR 수"는 시퀀스 값 차이가 아니라 실제 PR 문서 수다. 직접 푸시 커밋이 섞이면 두 값이 달라지므로 시퀀스 차이를 PR 수로 표기하지 않는다.
- **"직전"은 같은 시퀀스 공간에서 서수가 바로 아래인 릴리스다** (CR-030, DEV-155). 태그는 나중에 옛 커밋을 가리키며 생길 수 있어 시각 순서와 서수 순서가 어긋나고, 구간은 서수로 잘린다. 목록 정렬(시각)과 다를 수 있으므로 비교 대상 태그명을 함께 보여 준다. 서수가 가장 낮은 릴리스는 비교 대상이 없어 값이 없다 — 0으로 적지 않는다.
- **체인 밖 태그(`base_branch: null`)는 목록에 있으나 선택할 수 없다.** 숨기면 "그런 태그가 없다"로 오인된다 — 서수가 없어 앵커가 될 수 없다는 사실을 행에서 말한다.
- `release_not_indexed`는 오류가 아니라 수집 범위 문제다. 저장소 등록 상태 조회 경로(W-009)를 함께 제시한다. **W-009가 WP-034로 서면서 이 링크를 실제로 건다** (CR-050, DEV-159 해소) — `/repositories?repository=owner/name`으로 그 저장소의 진단으로 바로 보낸다. 두 원인(태그 없음 / 미수집)을 서버가 판별할 수 없다는 사실은 그대로이므로 안내 문구는 여전히 둘을 함께 말한다.
- 되돌림 보유 PR 수는 W-004와 같이 "준비 중 — 관계 파생(WP-030)"으로 둔다. 요약에 그 키가 없기 때문이다 (CR-027 DEV-133, CR-029 DEV-150).

- **집계가 세는 것은 PR이다** (CR-053). 목록은 PR과 커밋을 함께 보이므로 두 총계가 다를 수 있으며, 화면은 집계 패널에 그 사실을 밝힌다.

### 권한/정책

- 저장된 검색 실행 시 실행 사용자의 접근 범위가 적용된다. 저장자의 권한을 승계하지 않는다 (FR-SRCH-010 AC-3).
- **공유는 읽기·실행 권한이지 소유권이 아니다** (CR-049). 대상 팀의 구성원은 조회와 실행만 하며, 이름 변경·질의 수정·공개 범위 변경·삭제는 저장자만 수행한다. 공유받은 항목에는 그 액션을 그리지 않고, **화면이 그리지 않는 것에 의존하지 않는다** — 서버가 같은 규칙을 다시 강제한다.
- 목록·상세에서 볼 수 없는 항목과 존재하지 않는 항목을 구분해 알리지 않는다 (`NOT_FOUND` 하나로 답한다). 구분하면 남의 저장 검색이 있다는 사실 자체가 새어 나간다 (CR-049).
- **공유받은 항목의 시퀀스 인용 상태는 그 저장소를 볼 수 있을 때만 값을 갖는다** (CR-051, THR-043). 볼 수 없으면 `unavailable` 하나로 답하고 현재 에폭·공간 상태·재작성 여부를 적지 않는다 — 질의 문자열에 저장소 이름이 적혀 있다는 사실과 그 저장소의 현재 활동을 읽을 권한이 있다는 것은 다른 사실이다.

### 구현 메모

- 파싱 실패 질의는 실행 버튼을 비활성화하고 오류 구간을 표시한 채 편집으로 유도한다. **편집 경로는 저장자에게만 제시한다** — 공유받은 사람에게는 저장자가 고쳐야 한다는 사실을 알린다 (CR-049).
- 유효성 판정은 서버가 한다. 화면은 `@prs/query`로 입력을 미리 검증할 수 있으나 그것이 판정의 정본이 아니다 — 저장·수정·실행 모두 서버가 현재 문법으로 다시 검증한다 (CR-049).
- 무효가 된 질의를 화면이 자동으로 고치지 않는다. 고치는 것은 저장자의 뜻이다 (FR-SRCH-010 AC-6, CR-049).
- **낡은 에폭도 같은 규율을 따른다** (CR-051). 목록을 여는 것, 실행을 누르는 것, 이름을 고치는 것 어느 것도 저장된 에폭을 현재 값으로 옮기지 않는다. `unbound` 항목은 특히 그렇다 — **저장 당시의 에폭은 어디에도 없으므로 현재 값을 넣는 것은 복구가 아니라 추측이다.**
- 목록 한 페이지의 시퀀스 인용 상태는 **한 번에 판정한다.** 행마다 저장소·공간을 따로 조회하면 페이지 크기만큼 왕복이 생긴다 — 질의에서 뽑은 `repo:`·`base:` 쌍을 모아 일괄 조회한다 (ADR-009와 같은 규율).

### 권한/정책

### 권한/정책

- `operator` 역할이 전체를 본다. **`security_officer`는 진입하되 `A-001-ARCHIVE` 섹션만 렌더링한다**(`archive_only` 상태, FR-ING-010 AC-5). 두 역할 어느 쪽도 아니면 내비게이션 항목을 표시하지 않고 직접 진입 시 `no_permission`이다. **권한을 화면 단위로 넓히지 않는다** — `security_officer`에게 지표·실패 대기열·조정 스캔은 보이지 않으며, 그것이 `CR-050`이 `API-ADM-001`·`API-ADM-006`에서 내린 판단과 같은 규율이다 (CR-052, DEV-375).
- 재처리 실행은 감사 기록 대상이다.
- **원본 payload 열람도 감사 기록 대상이다** (`raw_event.view_payload`). 목록 조회 자체는 남기지 않는다 — 되돌릴 수 없는 노출은 원본을 펼친 요청뿐이고, 모든 조회를 남기면 그 신호가 묻힌다 (PR #66 리뷰).

### 구현 메모

- 지표는 30초 주기로 갱신하되, 사용자가 표를 조작 중일 때는 갱신을 보류해 스크롤·선택이 초기화되지 않게 한다.
- 일괄 재처리는 대상 건수를 확인 다이얼로그에 명시하고, 100건을 넘으면 재확인을 한 번 더 요구한다.

## A-002 저장소 등록 관리

### 화면 목적

수집 대상 저장소와 시퀀스 대상 브랜치를 관리한다.

### 진입 경로

- 좌측 내비게이션 "운영 > 저장소" (`operator` 한정)

### 섹션 정의

| 섹션 | 내용 | 관련 FR |
| --- | --- | --- |
| `A-002-LIST` 등록 목록 | 저장소, 등록 상태, 시퀀스 대상 브랜치, 미러 사용 여부, 백필 상태 | FR-ING-009 |
| `A-002-FORM` 등록·편집 | 저장소 식별자, 대상 브랜치(최대 10), 미러 사용, 백필 실행 여부 | FR-ING-009 |
| `A-002-REQUESTS` 등록 요청 | W-009에서 접수된 사용자 요청 목록과 그 처리. 정본은 `ENT-CORE-008`이며 WP-034가 그 표와 기록 경로(`API-ING-003`)를 세웠다. 운영자는 `pending` 요청을 먼저 보고, 요청받은 식별자로 `A-002-FORM`을 채워 실제 등록을 하거나 사유를 적어 종료한다. 처리 상태는 `pending`·`fulfilled`·`dismissed` 셋이고 처리자·처리 시각·처리 메모를 함께 보인다. **등록되지 않은 채 승인된 상태를 화면이 만들지 않는다** — "등록"은 `A-002-FORM`의 제출이며, 성공한 등록이 같은 식별자의 `pending` 요청 전부를 종료한다 (FR-ING-009 AC-11, CR-055) | FR-ING-009 |

### 주요 컴포넌트

`C-043 RepositoryRegistrationForm`, **`C-071 RegistrationRequestQueue`**, `C-013 ResultTable`, `C-004 EmptyState`

`C-013`은 `A-002-LIST`(등록 저장소 목록)의 것이고, `A-002-REQUESTS`는 **`C-071`을 쓴다** — `C-013`은 정렬 컨트롤을 갖고 행 타입이 `ResultRow`에 묶여 있어 요청 큐의 `onPrefill`·`onDismiss` 계약을 담지 못한다 (CR-055, PR #88 리뷰 P2)

### 상태 정의

`loading_initial`, `ready`, `empty_no_repository`, `error_no_access` (등록 대상에 접근 권한 없음), `error_branch_limit` (브랜치 10개 초과), `operation_pending` (등록·해제·요청 처리를 서버가 받는 중), `requests_empty` (처리할 등록 요청이 없음), `no_permission`, `auth_expired`, `offline`

### 이벤트 정의

| 이벤트 | 트리거 | 결과 |
| --- | --- | --- |
| `repo.register` | 등록 제출 | 저장소 등록, 선택 시 백필 잡 생성 |
| `repo.unregister` | 해제 클릭 | 수집 중단 (문서 유지, 확인 다이얼로그) |
| `repo.update_branches` | 브랜치 변경 | 시퀀스 대상 브랜치 갱신, 신규 브랜치마다 채번 잡 생성 (FR-ING-009 AC-12) |
| `request.prefill` | 요청 목록의 "등록" 클릭 | 요청받은 식별자로 `A-002-FORM`을 채운다. **이 조작만으로는 요청 상태가 바뀌지 않는다** — 등록이 성공해야 종료된다 |
| `request.dismiss` | 요청 목록의 "종료" 클릭 | 확인 뒤 그 요청을 `dismissed`로 종료하고 사유를 함께 기록한다 (감사 대상) |

### 권한/정책

- `operator` 역할만 접근한다. 등록·해제는 감사 기록 대상이다.

### 구현 메모

- 해제는 문서를 삭제하지 않는다는 사실을 확인 다이얼로그에 명시한다. 사용자가 "삭제"로 오해하면 데이터 손실을 우려해 해제를 회피한다.
- 시퀀스 대상 브랜치를 추가하면 그 브랜치의 전체 채번이 필요하다. **생성된 채번 잡과 그 진행률을 보이고, 예상 소요 시간을 지어내 표시하지 않는다** (CR-055, DEV-435) — 채번 시간은 브랜치의 커밋 수와 미러 상태에 달려 있어 폼이 그것을 알 수 없고, 근거 없는 예상치는 그것이 빗나가는 만큼 운영자의 판단을 망친다. 진행률은 A-003의 잡 목록과 같은 값이다.
- **등록 요청의 처리 메모는 `operator` 평면에만 있다.** 요청자에게 돌려주는 응답은 FR-ING-009 AC-10 그대로이며 처리 상태도 사유도 담지 않는다.

- 재채번은 비가역이며 기존 범위 인용을 무효화한다. 실행 전 영향 범위(무효화되는 안전 구간 표식 수, 영향받는 저장된 검색 수)를 산출해 확인 다이얼로그에 표시하고, 저장소 이름을 직접 입력하게 하는 2단계 확인을 요구한다.
- 재색인 진행 중에는 인덱스 상태 패널에 이중 쓰기 중임을 상시 표시한다.
- **잡마다 보이는 제어 버튼은 서버가 준 `allowed_actions`를 그대로 그린다** (FR-ADMIN-002 AC-7, CR-055). 화면이 상태 문자열로 가능한 동작을 추론하지 않는다 — 추론하면 전이 규칙이 두 곳에 살고, 러너가 실제로 지원하지 않는 동작을 화면이 제시한다.
- **인덱스 상태의 값 중 읽지 못한 것은 미확인으로 적는다** (FR-ING-008 AC-7). 크기를 모르는 것을 `0B`로 적으면 운영자가 인덱스가 비었다고 읽는다.
- **조정 스캔의 즉시 실행도 잡이다** (FR-ING-011 AC-7). 버튼을 누른 사실을 "스캔 완료"로 표시하지 않고 `queued`·`running`·진행률·종료 상태를 그대로 보인다.

```

### 상태

`empty`(capability 미선택), `loading`, `constraint_error`, `permission_denied`, `policy_blocked`, `unsupported_host`, `registry_stale`, `awaiting_confirmation`, `awaiting_approval`, `running`, `succeeded`, `failed`, `cancelled`, `timed_out`.

### 규칙

- 실제 토큰과 비밀 값은 argv 미리보기에 절대 노출하지 않는다. `<redacted>`로 표시한다.
- 미리보기 argv와 실제 실행 argv는 같은 구조화 명령 모델에서 파생한다. **argv 빌더는 하나뿐이다** (CR-008, ADR-017).
- 지원되지 않는 capability를 목록에서 숨기지 않는다.
- **폼 검증 규칙은 UI가 소유하지 않는다.** manifest의 의미 제약 모델을 폼·서버가 함께 읽고, 두 판정이 갈리면 실패로 본다 (CR-008, FR-GH-003 AC-8).
- **gh 출력을 원시 HTML로 렌더링하지 않는다.** ANSI CSI·OSC·제어 문자가 무해화된 뒤에만 화면에 닿는다 (CR-008, ADR-018).
- **실행기에서 브라우저 프로세스를 띄우지 않는다.** `--web` 계열은 URL을 돌려주고 사용자의 브라우저가 연다 (CR-008, ADR-019).
