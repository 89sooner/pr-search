# PR Search 보안 및 개인정보 아키텍처

> 상태: review | 버전: v1.12 | 갱신일: 2026-09-15

CR-079: WP-074는 기존 읽기 Data App만 사용한다. 신규 증거 proof의 허용 필드는 [설계](pr_search_wp074_design.md) 6절, 측정 read-only role·세션 파일·비식별 출력은 측정 가이드가 정본이다. 새 제목 쓰기 App, OIDC 정책 변경, 익명 조회, fixture를 production 직접 확정에 넣는 경로는 만들지 않는다. 기존 auth gate와 범위 밖=미등록 404를 유지한다.

## 1. 목적

신뢰 경계, 인증, 권한, 정책, 시크릿, 감사, 개인정보, 위협 모델, 오남용 사례를 정의한다. 근거 요구사항은 FR-AUTH-001~004, NFR-005, NFR-006이며, 권한 강제 방식은 ADR-008을 따른다.

## 2. 보안 설계 원칙

1. **PR Search는 GHE의 접근 통제를 확장하지 않는다.** 이 시스템에서 볼 수 있는 것은 GHE에서 볼 수 있는 것의 부분집합이어야 한다. 파생 시스템이 원본보다 넓은 시야를 주면 그 자체가 접근 통제 우회다.
2. **기본 거부.** 접근 범위를 확인할 수 없으면 아무것도 반환하지 않는다. 만료된 캐시로 대신하지 않는다.
3. **존재 여부도 정보다.** 접근 범위 밖 리소스는 403이 아니라 404다.
4. **건수와 집계도 정보다.** 문서를 숨기는 것으로 부족하며, 총 건수·패싯·집계에서도 제외해야 한다.
5. **소스 코드를 저장하지 않는다.** 이 원칙을 문서 매핑 수준(`dynamic: strict`)에서 구조적으로 강제한다. 운영 실수로도 코드가 색인되지 않게 한다.
6. **읽기 전용이 기본값이다.** GHE에 대한 쓰기 권한은 명시적으로 승인된 두 경로에서만, 그것도 조회 자격 증명과 분리해 요청한다 — 사용자가 지시한 실행(10장 Operations Plane, CR-005)과 M 넘버 표기라는 시스템 자동 쓰기(13장, CR-077) 둘뿐이다. 최소 권한 원칙의 가장 강한 형태는 그 둘 바깥에서는 여전히 쓰기 권한을 애초에 요청하지 않는 것이다.

## 3. Trust Boundaries

| Boundary | 신뢰 수준 | 통제 | 관련 요구사항 |
| --- | --- | --- | --- |
| 사용자 브라우저 | untrusted | HttpOnly·Secure·SameSite 세션 쿠키, CSP, 토큰 미노출 | FR-AUTH-001 |
| Next.js 서버 (`web`) | controlled | 세션 검증, 클라이언트 헤더 미전달, 프록시 | ADR-011 |
| `search-api` | controlled | 역할 검사, 접근 범위 강제 결합, 감사 | FR-AUTH-002, FR-AUTH-004 |
| `ingest-gateway` | 공개 엔드포인트, 요청 untrusted | HMAC-SHA256 서명 검증, 크기 상한, 파싱 전 검증 | FR-ING-001 |
| `pipeline-worker` | trusted (내부) | 네트워크 정책으로 외부 인바운드 차단 | - |
| PostgreSQL / Elasticsearch / Redis | trusted (내부) | 사설 네트워크, 인증, TLS | NFR-005 |
| git mirror 볼륨 | trusted (내부) | 워커만 마운트, 읽기 전용 fetch | ADR-005 |
| GitHub Enterprise | 외부 신뢰 당사자 | App 토큰, TLS, 웹훅 시크릿 | 외부 인터페이스 |
| OIDC IdP | 외부 신뢰 당사자 | 토큰 서명·발급자·대상·만료 검증 | FR-AUTH-001 |

`ingest-gateway`가 유일한 공개 인바운드 지점이다. 그래서 이 경로만 "요청은 신뢰하지 않되 엔드포인트는 노출된다"는 특수한 위치에 있고, 서명 검증을 **본문 파싱 이전에** 원문 바이트로 수행한다.

## 4. 인증

| 항목 | 결정 |
| --- | --- |
| 프로토콜 | OIDC Authorization Code + PKCE |
| 세션 | 서버 측 세션 + HttpOnly·Secure·SameSite=Lax 쿠키. 운영에서 `Secure`를 끄는 면제는 적어 낸 선언 둘뿐이다 — `AUTH_ENABLED=false`(CR-083), `ALLOW_INSECURE_COOKIES=true`(CR-091, 평문 HTTP 파일럿). `Secure`가 없는 쿠키는 `__Host-` 접두 없이 발급한다 |
| 유휴 만료 | 8시간 |
| 절대 만료 | 12시간 |
| 토큰 검증 | 서명, `iss`, `aud`, `exp`, `nonce` 전부 검증 |
| 로그아웃 | 서버 측 세션 무효화 (쿠키 삭제만으로 끝내지 않음). `POST`만 받는다. 셸의 사용자 메뉴가 폼으로 제출하고 문서 요청은 303으로 공개 완료 화면을 받는다. IdP 세션은 끝내지 않는다 (CR-092) |
| 세션 저장 | Redis (PostgreSQL 백업 없음 — 세션 유실은 재로그인으로 복구) |

세션 만료 시 현재 경로를 `state`에 담아 인증 후 복귀시킨다 (FR-AUTH-001 예외 처리). 조사 중이던 화면으로 돌아가지 못하면 사용자는 조사를 처음부터 다시 한다.

**신원이 `search-api`에 닿는 방법 (CR-015, DEV-047).** OIDC 흐름은 `web`만 수행한다 — 인프라 문서의 아웃바운드 허용 목록이 IdP를 `web`에만 열어 준다. 그런데 강제 접근 범위 필터를 거는 곳은 `search-api`다. 그래서 신원이 두 서비스를 건너야 하는데, `X-User-Id` 같은 헤더로 건네면 클러스터 안에서 `search-api`에 닿을 수 있는 무엇이든 신원을 위조할 수 있다.

- `web`은 프록시할 때 **세션 쿠키와 상관 ID만** 허용 목록으로 전달한다. 나머지 클라이언트 헤더는 전달하지 않는다 (ADR-011).
- `search-api`는 그 쿠키를 **같은 Redis 세션 저장소에서 직접 해석한다.** 세션이 서버 측에 있으므로 위조한 쿠키 값은 아무 세션도 열지 못한다.
- `search-api`는 신원을 주장하는 어떤 헤더도 읽지 않는다. 읽는 순간 그 헤더가 우회 경로가 된다.

두 서비스가 세션을 각각 검증하는 것은 중복이 아니라 의도다. `search-api`가 "`web`을 거쳐 왔다"는 사실에 기대면, 그 가정이 깨지는 날(디버그 포트, 사이드카, 잘못된 네트워크 정책) 통제가 통째로 사라진다.

**평문 HTTP 파일럿 (CR-091, DEV-694).** 사내 `0.1.0-pilot.6`은 TLS 없이 GHE 로그인을 시험해야 했고, `CR-083`의 면제(인증을 끈 배포)로는 그것을 할 수 없었다. `SESSION_COOKIE_SECURE=false`와 `ALLOW_INSECURE_COOKIES=true`를 **함께** 적은 배포는 인증을 켠 채 선다. 플래그 하나로는 아무것도 바뀌지 않으며 인식하지 못하는 값은 기동을 거부한다. 그 형상은 `web`이 기동할 때마다, `prsctl health`가 실행할 때마다 경고한다 — 받아들인 위험이 한 번 적히고 잊혀 운영 형상이 되지 않게 한다(THR-052).

- **쿠키 이름이 `Secure` 여부를 따른다.** 브라우저는 `__Host-` 접두 쿠키에 `Secure`가 없으면 저장하지 않는다. 그래서 세션 쿠키는 `__Host-prs_session`/`prs_session`, 로그인 왕복 쿠키는 `__Host-prs_oidc`/`prs_oidc`로 갈리며, 세우는 자리와 읽는 자리가 같은 함수로 이름을 고른다. 속성만 풀고 이름을 두면 면제가 문서에만 있다.
- **서비스 사이에는 정본 이름 하나다.** `web`의 프록시는 브라우저가 어떤 이름으로 보냈든 `search-api`로 가는 헤더를 `__Host-prs_session`으로 다시 조립한다. `search-api`는 그 이름만 읽고 이 면제를 알지 못한다.
- **중복 쿠키는 web에서도 거절한다** (독립 검토 A). `search-api`의 쿠키 읽기는 같은 이름이 둘 이상이면 거절하는데(쿠키 주입 방어), web이 프레임워크의 `cookies.get()`으로 하나를 골라 다시 조립하면 그 방어가 브라우저 구간에서 사라진다. 접두 없는 이름은 하위 도메인이나 같은 망에서 하나 더 심을 수 있으므로 **세션 강요**(피해자의 요청이 남의 세션으로 실행된다)의 입구가 된다. 그래서 관문·프록시·Operations 콜백은 원시 `Cookie` 헤더를 같은 규칙으로 읽어 중복이면 세션이 없는 것으로 보고, 로그인 콜백은 중복 왕복 쿠키로 로그인을 완결하지 않으며, 로그아웃은 같은 이름의 세션을 전부 끝낸다.
- TLS 배포의 쿠키 이름과 속성은 바뀌지 않는다 — 이 판을 받는 것만으로 로그인한 사용자의 세션이 끊기지 않는다.

**복귀 주소는 경로만 담는다 (CR-092, DEV-699).** 로그인 콜백과 Operations 계정 연결 콜백의 `Location`에 호스트를 싣지 않는다. `next start`는 요청 출처를 자기가 들은 호스트·포트로 조립하므로 역방향 프록시 뒤에서 절대 주소는 `localhost:3000`이 됐다 — 사내 `0.1.0-pilot.7` 이미지에 `Host`를 넘겨도 `https://localhost:3000/…`이었다(실측). 그것을 고치려고 `Host`·`X-Forwarded-Host`를 믿으면 그 헤더를 고른 누구든 복귀 목적지를 고른다(THR-054). 브라우저는 경로만 담은 `Location`을 자기가 연 주소로 풀므로 서버가 외부 이름을 알 필요가 없다. 경로는 `sanitizeReturnPath`의 규칙(같은 출처의 절대 경로, `//`·`/\`·제어 문자 거부)을 지나야 하고, 어긴 값은 조용히 고치지 않고 오류로 던진다. 라우트 핸들러가 요청 출처로 주소를 조립하지 않는다는 것을 정적 시험이 건다.

**로그아웃의 경계 (CR-092, DEV-700).** 로그아웃은 `POST`만 받는다 — `GET`이면 다른 사이트의 `<img>` 하나로 사용자가 로그아웃된다. 셸의 사용자 메뉴는 폼을 제출하고, 라우트는 같은 이름의 서버 세션을 전부 끝낸 뒤 문서 요청에 303으로 `/auth/signed-out`을 가리킨다(스크립트 요청은 JSON 그대로). 완료 화면은 세션을 읽지 않고 셸을 세우지 않는다 — 셸의 내비게이션은 로그인으로 이어지고, IdP 세션이 살아 있으면 곧바로 다시 로그인되기 때문이다. **PR Search는 IdP 세션을 끝내지 않으며** 완료 화면이 그 사실을 말한다(공용 PC에서 다음 사람이 「다시 로그인」 한 번으로 앞사람 계정에 들어가지 않게). 로그아웃 요청에도 CSRF 토큰은 없다(`DEV-691`). 다른 사이트의 폼 POST에는 `SameSite=Lax` 세션 쿠키가 실리지 않아 서버 세션을 끝낼 수 없지만, 강제 로그아웃(응답의 쿠키 만료)까지 막는다고 주장하지 않는다 — 토큰 체계를 들이는 판이 함께 닫는다.

## 5. 권한 모델

### 5.1 역할

| 역할 | 부여 방식 | 권한 |
| --- | --- | --- |
| `developer` | 기본값 (인증된 모든 사용자) | 접근 범위 내 조회, 저장된 검색 관리 |
| `release_manager` | 관리자 지정 | developer + 안전 구간 표식 쓰기 |
| `manager` | IdP 그룹 매핑 | developer와 동일 (집계 화면 사용) |
| `qa` | IdP 그룹 매핑 | developer와 동일 |
| `operator` | 관리자 지정 | 운영 콘솔 쓰기(A-001~A-003), 전 저장소 운영 데이터 조회, GitHub Operations 레지스트리·운영 정책 조회와 변경(A-005·A-006 — CR-090) |
| `security_officer` | 관리자 지정 | 감사 로그 조회(A-004), GitHub Operations 레지스트리·운영 정책 조회(A-005·A-006, 변경 없음 — CR-090) |

역할은 두 곳에서 오고 **합집합으로 합친다 (CR-015, DEV-049).** IdP 그룹 클레임은 `manager`·`qa`로만 매핑하고, `operator`·`release_manager`·`security_officer`는 `app_user.roles[]`의 DB 지정값만 쓴다. 최종 역할 = {`developer`} ∪ (IdP 그룹 매핑) ∪ (DB 지정값).

**합집합은 요청마다 성립한다 (CR-091, DEV-695).** 로그인 콜백을 도는 `web`은 DB에 닿지 않으므로 세션에는 IdP·팀 매핑 절반만 담긴다. 나머지 절반은 `search-api`가 세션을 읽을 때마다 `app_user.roles[]`에서 더하고(세션에 되써 넣지 않는다), 화면 관문은 그 결과를 `/me`(API-AUTH-001)에서 받는다. 그래서 부여도 회수도 다음 요청부터 반영되고 회수가 세션 수명(최대 12시간) 동안 늦어지지 않는다. 관리자 지정을 읽지 못하면 세션의 역할만으로 판정한다 — 지정값은 권한을 더하기만 하므로 빠진 쪽의 결과는 거절이다. **이 합집합이 `CR-015`부터 문서에만 있었다** — 콜백이 지정값 자리에 빈 배열을 넘겼고 세션을 읽는 두 자리가 세션의 역할만 봤으며, 지정값을 쓰는 운영 경로도 없어 세션 인증으로 바꾼 사내 배포에서 누구도 `operator`가 될 수 없었다.

**관리자 지정은 배포 호스트의 `prsctl role grant|revoke <login 또는 user_id> <역할>`로만 바꾼다.** 지정할 수 있는 역할은 `release_manager`·`operator`·`security_officer`이고 대상은 한 번 로그인해 정본에 행이 있는 사용자다. 로그인 이름이 대소문자만 다른 여러 행(개명 흔적)에 걸리면 **대소문자까지 같은 행이 있어도 고르지 않고** 후보의 `user_id`와 마지막 접속을 보여 준다 — 운영 권한이 쓰이지 않는 행에 붙지 않게 `user_id`로 다시 가리킨다. 역할 변경과 감사 한 행(`user_role.grant`·`user_role.revoke`, 행위 주체 `prsctl:<호스트 사용자>`)이 한 트랜잭션이며, 바뀐 것이 없는 재실행은 아무것도 쓰지 않는다. **최초의 `operator`는 화면으로 만들 수 없으므로** 이 경로가 출발점이다. 호스트에서 `prsctl`을 돌릴 수 있는 사람은 이미 DB와 시크릿을 쥔 경계 안에 있으므로 이 명령이 새 권한 경계를 열지 않는다. 역할 관리 화면은 범위 밖이다.

방향을 어느 쪽으로든 틀리면 조용히 위험해진다. IdP 클레임으로 `roles[]`를 덮어쓰면 관리자가 지정한 `operator`가 다음 로그인에 사라지고, 반대로 IdP 그룹을 `operator`까지 믿으면 그룹을 만들 수 있는 사람이 운영 권한을 발급할 수 있게 된다.

역할은 **화면·액션 접근**만 결정한다. **데이터 범위**는 역할과 무관하게 접근 범위가 결정한다. `operator`도 권한 없는 저장소의 PR 본문은 볼 수 없다 (SRS 6장).

### 5.2 접근 범위

접근 범위(`access_scope`)는 사용자가 GHE에서 read 이상 권한을 가진 저장소 ID 집합이다 (FR-AUTH-002 AC-1).

```text
resolveAccessScope(user)
  ├─ Redis 조회 (TTL 5분)          → 적중 시 반환
  ├─ PostgreSQL permission_cache   → 5분 이내면 Redis 채우고 반환
  └─ GHE API 조회
      ├─ 성공 → Redis + PostgreSQL 갱신 후 반환
      └─ 실패 → 오류 (503). 만료 캐시를 쓰지 않는다 (AC-3)
```

저장소 500개 초과 시 `scope_kind: 'org_team'`으로 전환한다 (AC-6).

**조직·팀은 `org_team` 범위에서만 읽는다 (CR-092, DEV-698).** 표현은 그 범위 자신의 저장소 수가 고르므로(`toAccessScope`, 캐시의 `scope_kind`), 500개 이하인 범위의 조직·팀 값은 필터에도 무효화 대상 조회(`org_ids`는 `org_team` 행에서만, `team_ids`는 읽지 않음)에도 쓰이지 않는다. 그 조회를 늘 함께 하던 판에서는 App에 조직 `Members` 권한이 없으면 **쓰이지 않는 조회 하나가 범위 전체를 503으로 만들었다**(사내 `0.1.0-pilot.7`, 저장소 셋). 이제 출처는 저장소마다 실효 권한(협업자 권한 API, 저장소 `Metadata` 읽기)을 먼저 읽고, 500개를 넘을 때만 조직 구성원·팀 목록·팀 소속(조직 `Members` 읽기)을 읽는다. 그 조회의 실패는 여전히 503이다 — 부분 범위를 내지 않는다(FR-AUTH-002 예외 처리). **실패의 사유는 응답이 아니라 운영 로그에 남긴다**: 실패한 단계, `@prs/github`의 오류 분류, 상태 코드, 그 단계가 요구하는 App 권한. GHE 응답 본문은 싣지 않는다 — 전송 오류의 메시지가 본문 앞부분을 담기 때문이다. 권한 표는 런북 2.C다.

| scope_kind | 결합되는 필터 |
| --- | --- |
| `explicit` | `terms: { repository_id: [...] }` |
| `org_team` | `bool.should`: (`org_id` in 사용자 조직 AND `visibility` in [`public`,`internal`]) OR (`allowed_team_ids` in 사용자 팀) |

`org_team` 모드가 `explicit`보다 넓은 범위를 주지 않도록, 전환 시 두 방식의 결과 집합이 동일함을 검증하는 테스트를 둔다.

### 5.3 강제 결합 지점

모든 Elasticsearch 조회는 `applyMandatoryScopeFilter`를 통과한다 (ADR-008). 이를 타입 시스템으로 강제한다.

```ts
// packages/es
type ScopedQuery = EsQuery & { readonly __scopeApplied: unique symbol };

export function applyMandatoryScopeFilter(q: EsQuery, scope: AccessScope): ScopedQuery;
export function search(q: ScopedQuery): Promise<EsResponse>;   // ScopedQuery만 받는다
```

`search`가 `ScopedQuery`만 받고 `ScopedQuery`는 `applyMandatoryScopeFilter`만 만들 수 있으므로, 권한 필터를 건너뛴 조회는 컴파일되지 않는다. 아키텍처 테스트로 이 불변식을 추가 검증한다.

**PostgreSQL을 읽는 사용자 대면 경로에는 이 타입 강제가 닿지 않는다** (CR-027 DEV-130, CR-050 DEV-353). 시퀀스 조회(`API-SEQ-006`)와 저장소 진단 조회(`API-ING-002`)는 정본이 `repository` 표라 `ScopedQuery`를 거치지 않으며, 그 자리를 `isRepositoryInScope`가 메운다. 두 규칙이 같은 판정을 하도록 **하나의 함수만** 쓰고, 저장소 행을 얻는 통로가 그 함수를 반드시 지나게 해서 빠뜨릴 자리를 없앤다.

**판정에 넘기는 재료가 빠지면 함수는 조용히 좁게 답한다.** `isRepositoryInScope`의 `allowedTeamIds`는 선택 인자이고 없으면 빈 배열로 읽히므로, 넘기지 않으면 `org_team` 범위에서 **팀 소속으로만 허용되는 비공개 저장소가 결과에서 사라진다.** 유출이 아니라 누락이므로 접근 통제 시험은 통과하지만, 사용자에게는 "등록되지 않았다"는 **틀린 진단**으로 보인다 — W-009에서는 그 오독이 곧 이 화면의 실패다. 그래서 `repositoryId`·`orgId`·`visibility`·`allowedTeamIds` 넷을 항상 함께 넘기며, `explicit`와 `org_team` 두 표현이 같은 논리 권한 집합에서 **같은 결과**를 내는 것을 회귀가 건다.

**앞 단계에서 확인했다는 이유로 뒤 단계의 필터를 생략하지 않는다.** `API-ING-002`는 PostgreSQL에서 이미 접근 범위를 거른 저장소들의 문서 수를 Elasticsearch에서 집계하는데, 그 집계도 `applyMandatoryScopeFilter`를 다시 지난다. 생략은 한 번 허용되면 그 자리가 곧 우회 경로가 되고, 두 단계의 판정 기준이 갈라지는 순간 조용히 범위 밖 문서를 세게 된다.

### 5.4 권한 캐시 무효화

| 트리거 | 대상 | 지연 |
| --- | --- | --- |
| TTL 만료 | 해당 사용자 | 최대 5분 |
| `member` 웹훅 (조직 멤버 변경) | 해당 사용자 | 즉시 |
| `team` 웹훅 (팀 멤버·권한 변경) | 팀 전원 | 즉시 |
| `repository` 웹훅 (가시성·협업자 변경) | 영향 사용자 | 즉시 |
| 관리자 수동 무효화 | 지정 사용자 또는 전체 | 즉시 |

대량 무효화(팀 전원) 시 GHE 조회 폭주를 막기 위해 사용자 단위 요청 병합과 동시 요청 상한(기본 20)을 적용한다 (FR-AUTH-003 예외 처리).

**무효화와 갱신이 겹칠 때 (CR-015, DEV-044).** 무효화는 캐시를 지우는 것만으로 끝나지 않는다. 회수 직전에 시작된 GHE 조회가 회수 뒤에 끝나면 회수 이전의 범위를 캐시에 다시 써 넣고, 그 사용자는 5분 더 조회할 수 있다 — FR-AUTH-003 AC-4가 금지하는 바로 그 상황이다.

`app_user.access_scope_version`이 울타리다.

1. 갱신을 시작할 때 현재 `access_scope_version`을 읽어 둔다.
2. 무효화는 캐시 삭제와 함께 이 값을 증가시킨다.
3. 갱신이 끝나 캐시에 쓸 때, 읽어 둔 값이 그대로일 때만 기록한다. 달라졌으면 결과를 버린다.

버린 결과는 손실이 아니다. 다음 요청이 캐시 미스로 다시 조회하고, 그때는 회수가 반영된 범위를 얻는다.

| 연결 | 접속 주체 | 권한을 집는 방법 |
| --- | --- | --- |
| `DATABASE_URL` (전 서비스) | `prs_app` 멤버십을 가진 **로그인 롤** | 그 주체의 **세션 기본 역할**을 `prs_app`으로 둔다 |
| `ADMIN_DATABASE_URL` (`JOB-AUD-001`) | `prs_admin` 멤버십을 가진 **로그인 롤** | 연결 직후 `SET ROLE prs_admin` (DEV-416) |

```sql

ALTER ROLE prs_app_login SET role = 'prs_app';
```

**소유자 계정을 그대로 쓰지 않는다.** 그 계정은 모든 표에 전권을 가지므로 `prs_app`이 지키는 제약(감사 기록 `UPDATE`·`DELETE` 금지, `FR-AUTH-004` AC-3)을 통째로 우회한다. **주체 생성은 마이그레이션이 아니라 운영 프로비저닝의 몫이다** — 비밀번호가 시크릿이기 때문이다.

**운영 정책 변경은 이 두 연결을 늘리지 않는다 (CR-090).** 운영자의 승인·차단은 `DATABASE_URL`(`prs_app`)로 들어오지만 `prs_app`에는 정책 표 쓰기 권한이 없고, 마이그레이션 030의 `SECURITY DEFINER` 함수 하나만 실행할 수 있다. `search-api`·web에 `ADMIN_DATABASE_URL`을 주지 않는다. 경계와 한계는 10.6절이다.

**Profile A의 시크릿 파일** (CR-059 / ADR-021, DEV-499). Kubernetes Secret이 없는 형상이므로 저장 수단을 여기서 정한다 — **정하지 않으면 운영자가 임의로 정하고, 그 임의값이 반입 번들에 섞여 나가는 것이 `NFR-005`가 막으려는 경로다.**

- 호스트의 별도 파일에 두고 **소유자만 읽도록 권한을 좁힌다.** 값은 사내 시크릿 관리에서 주입한다.
- **저장소에 커밋하지 않으며, 어떤 오프라인 번들에도 담지 않는다.** 번들이 담는 것은 `.env.example`뿐이고 값이 채워진 파일은 반입 대상이 아니라 사내에서 만드는 것이다.
- 회전 주기와 감사 규칙은 프로파일과 무관하게 위 표 그대로다. 회전 수단만 `kubectl`에서 파일 교체 + 컨테이너 재시작으로 바뀐다.
- **Compose 정의 파일 자체에 시크릿 리터럴을 쓰지 않는다.** 모든 값이 환경 참조(`${VAR}`)여야 하며 `WP-070`이 그 검사를 자동화한다. **`docker compose config` 출력으로 판정하지 않는다** — 그 명령은 정의상 `.env` 값을 치환해 보여 주므로 시크릿이 나타나는 것이 정상이고, 그것을 위반으로 세면 통과할 수 없는 검사가 된다.
- **번들을 받는 데 쓰는 GitHub 읽기 토큰은 `.env`에 넣지 않는다** (CR-063 / `WP-072`). 이 저장소 한정 fine-grained PAT(Contents: Read-only)이며 `gh release download`를 실행하는 순간에만 환경 변수(`GH_TOKEN`)로 준다. 서비스는 그 토큰을 읽지 않고, `.env.example`·번들·런북에 값이 들어갈 자리가 없다 — 회귀 시험이 `.env.example`에 그 키가 없음을 확인한다.

규칙:

- 시크릿을 로그·응답·오류 메시지·문서에 남기지 않는다. 로그 스캔을 배포 게이트로 둔다 (NFR-005).
- 웹훅 시크릿 회전은 무중단이어야 한다. 회전 기간 동안 구·신 두 값 모두로 서명 검증을 시도한다.
- 커서 봉인 키 회전은 진행 중인 페이징을 무효화한다. 클라이언트는 `CURSOR_INVALID`를 받고 첫 페이지로 복귀한다.
- 로컬 개발 환경에는 실제 시크릿을 두지 않는다. 개발용 GHE 인스턴스 또는 픽스처를 쓴다.

## 7. 감사 모델

모든 중요 액션은 행위자, 리소스, 행위, 결정, 결과, 요청 ID, 시각을 남긴다 (FR-AUTH-004).

**감사 대상의 정본은 이 문서가 아니다 (CR-054, DEV-400·401).** `srs_final.md` FR-AUTH-004 AC-1의 「감사 대상 액션 정본」 표가 유일한 정본이며, 이 장은 그것을 **인용하고 넓히지 않는다.** 이전 판은 여기에 표를 따로 두어 SRS가 승인한 적 없는 액션 넷을 담고 있었고, 그중 `secret.rotate`는 소유하는 제품 기능 자체가 없었다 — 파생 문서가 승인 범위를 넓히면 그 확장은 아무의 결정도 아닌 채로 구현 요구가 된다.

**개수를 여기에 적지 않는다.** 이전 판을 인용한 `WP-039`가 "13종"이라 적는 동안 표는 14행이었고 그 행들이 담은 `action` 문자열은 18개였다. 셋 중 어느 것도 틀리지 않았고 **셋이 서로 다른 것을 세고 있었다.** 개수가 필요하면 정본 표에서 그때그때 센다.

### 7.1 감사 기록 규칙

- 감사 기록은 갱신·삭제되지 않는다. 애플리케이션 DB 롤에 `UPDATE`/`DELETE` 권한을 부여하지 않는다 (AC-3).
- 보존 1년. 만료 삭제는 별도 관리 롤이 파티션 드롭으로 수행하고 그 자체가 감사 대상이다 (`retention.purge`, `JOB-AUD-001`).
- 조회는 `security_officer` 역할로 제한한다 (AC-5). 감사 화면 진입 자체도 감사 대상이다 (`audit.view`, AC-8).
- 질의 문자열은 감사에 남기지만, **응답 본문은 남기지 않는다.** 감사 로그가 데이터 유출 경로가 되면 안 된다.
- `target`·`query`가 의미상 없는 액션은 그 칸을 **비운다** (AC-2). `N/A`나 빈 문자열로 지어내면 "없다"와 "모른다"가 같은 모양이 된다.
- **운영 평면에만 있는 값이 감사 기록을 통해 새어 나가지 않는다** (CR-055). `repository_registration_request.dismiss`의 종료 사유는 감사에 남지만, 감사 조회는 `security_officer` 전용이므로 요청자에게 도달할 경로가 없다. 새 감사 액션을 더할 때마다 **그 `detail`이 어느 평면의 값인지**를 함께 판정한다.

### 7.2 실패 격리 (AC-6)

**감사 쓰기는 주 동작의 트랜잭션 밖에 있고, 그 실패가 주 동작의 결과를 바꾸지 않는다.** 주 동작이 200이면 200으로, 403이면 403으로 응답한다 — 감사 실패 때문에 500이 되어서는 안 되고, 반대로 주 동작의 실패를 감사 성공이 덮어서도 안 된다.

**"비동기"가 뜻하는 것은 그것뿐이다 (CR-054).** 관측되지 않는 Promise, 프로세스 종료 시 유실되는 fire-and-forget, 새 큐나 브로커를 요구하지 않는다. 신뢰도를 위해 DB 쓰기를 기다려도 되며, **기다리는 것은 지연이고 전파하는 것은 결합**이다 — 금지되는 것은 후자다.

실패는 `audit_record_failed_total` 지표로 센다. 5분 이상 지속되면 P2 경보(`RB-18`)가 뜬다 — 관측성 문서 5장이 그 규칙의 정본이다.

**호출부마다 각자 `try`/`catch`를 쓰지 않는다.** 공용 경계 하나(`recordAuditBestEffort`)가 그 책임을 갖는다. 각자 구현하면 빠뜨린 자리가 리뷰에서 눈에 띄지 않으며, 실제로 `WP-039` 착수 전 감사에서 호출부 넷 중 하나만 격리돼 있었다 (DEV-406).

**예외 하나 — 운영 정책 변경 (CR-090, FR-AUTH-004 AC-6 예외).** GitHub Operations의 운영 승인·철회·차단·재개가 **적용**되면 그 감사 한 행은 변경과 같은 트랜잭션(DB 함수 안)에서 쓰고, 감사를 남기지 못하면 변경도 커밋되지 않는다. 실행을 여는 결정이 기록 없이 적용되는 쪽이 결정이 거절되는 쪽보다 나쁘기 때문이다. 거절은 상태를 바꾸지 않으므로 이 절의 규칙(`recordAuditBestEffort`)을 그대로 따른다 — 액션을 본문 `action`에서 정하므로 그 값이 없거나 네 값이 아닌 요청은 남기지 않는다. 상세는 10.6절이다.

### 7.3 어휘 (AC-7)

**신규 기록은 정본 표의 `action` 값만 쓴다.** 그러나 AC-3이 과거 기록의 갱신을 금지하므로, **조회는 표에 없는 과거 값도 필터할 수 있어야 한다.**

| 구분 | 규칙 |
| --- | --- |
| 쓰기 어휘 | 정본 표의 값만. 코드는 공유 상수에서 가져온다 |
| 읽기 이력 어휘 | 저장된 임의 문자열. `API-ADM-005`의 `action` 필터가 enum으로 좁혀지면 과거를 조사할 수 없다 |
| legacy 값 | `sequence_integrity.reassign` (WP-028이 기록했다). 다시 쓰지 않고 지우지도 않는다 |

쓰기 어휘를 좁히는 일이 읽기 이력을 잘라 내는 일이 되어서는 안 된다 — 감사의 목적이 과거를 조사하는 것이기 때문이다.

- 이메일은 PostgreSQL에만 두고 Elasticsearch 문서에는 넣지 않는다. 검색·집계에 필요하지 않다.

## 9. 웹훅 수신 보안

`ingest-gateway`는 유일한 공개 인바운드 지점이므로 별도로 다룬다.

| 통제 | 구현 |
| --- | --- |
| 서명 검증 | `X-Hub-Signature-256`을 원문 바이트로 HMAC-SHA256 계산, 상수 시간 비교 (FR-ING-001 AC-1) |
| 검증 시점 | **JSON 파싱 이전.** 파싱 후 검증하면 파서가 미검증 입력에 노출된다 |
| 크기 상한 | 25MB. 초과 시 413, 본문을 읽지 않고 종료 (AC-6) |
| 미검증 payload 저장 | 하지 않음. 서명 실패 시 저장 없이 401 (AC-2) |
| 재생 공격 | `delivery_id` 유일 제약이 중복 처리를 차단 (FR-ING-002) |
| 네트워크 | 사내망 한정. GHE 인스턴스 IP 대역으로 인그레스 제한 |
| 속도 제한 | IP당 상한. 단, GHE 재전송을 막지 않도록 넉넉하게 설정 |
| 오류 응답 | 내부 정보를 노출하지 않는다. 401/413/500만 반환 |
| 거부 지표 | `ingest_rejected_total` 5분간 10건 초과 시 경보 (공격 신호) |

## 9.1 gh 실행 출력·파일 경계 (CR-008)

`ingest-gateway`가 유일한 공개 인바운드 지점이라면, `gh-executor`의 출력은 유일하게 **외부에서 온 텍스트가 사용자 화면까지 직행하는 경로**다. 그래서 따로 다룬다.

| 통제 | 구현 |
| --- | --- |
| 신뢰 가정 | gh 출력과 GitHub 텍스트는 신뢰하지 않는다. gh 2.97.0 자체도 외부 입력이 섞인 터미널 escape 처리 문제를 보안 수정한 이력이 있다 |
| 무해화 지점 | 실행기와 UI 사이의 `SafeGhOutput` 경계 한 곳. 렌더링 지점마다 붙이지 않는다 (ADR-018) |

| 기타 제어 문자 | 제거 또는 escape |
| Markdown | 안전 렌더러만. 원시 HTML 실행 금지 |
| 프런트엔드 | gh 출력에 `dangerouslySetInnerHTML` 금지 |
| invalid UTF-8 | 대체 문자로 치환 |
| 출력 크기 | 바이트 상한 후 절단 표시 |
| 바이너리 출력 | 탐지해 텍스트로 렌더링하지 않음 |
| 스트리밍 | 청크 경계에서 분할된 escape 시퀀스를 복원 후 처리 |
| 파일 경로 | workspace 안으로 정규화·강제. `..`·절대 경로·symlink 탈출 차단 |
| 아티팩트 | 파일시스템 경로가 아니라 아티팩트 ID로 전달. 파일명 정규화 |
| workspace | 실행 단위 격리, 용량 할당량, 실패 시 부분 파일 정리, 종료 후 폐기 |

| THR-007 | 권한 회수 후에도 캐시로 계속 조회 | 접근 통제 우회 | TTL 5분 + 권한 이벤트 즉시 무효화 (FR-AUTH-003) |
| THR-008 | GHE 토큰 탈취 후 API 남용 | 광범위 데이터 접근 | 읽기 전용 App 권한, 토큰 1시간 만료, 시크릿 저장소 격리, 회전 |
| THR-009 | 로그·오류 응답에 토큰·시크릿 노출 | 자격 증명 유출 | 로그 스캔 배포 게이트, 구조화 로깅 시 필드 화이트리스트 |

## 10. GitHub Operations Plane 보안 (CR-005 신규)

기존 보안 설계는 "GHE 읽기 전용"을 전제로 했다. CR-005로 쓰기 경로가 생겼으므로 이 장이 그 전제를 대체한다.

### 10.1 두 개의 자격 증명 경계

| 경계 | Data App | Operations App |
| --- | --- | --- |
| 인증 방식 | GitHub App 설치 토큰 (server-to-server) | GitHub App 사용자 액세스 토큰 (user-to-server) |
| 권한 | 최소 read | 명시적으로 필요한 권한만 |
| 사용처 | 웹훅 보강, 백필, 권한 조회 | 사용자가 요청한 작업 실행 |
| 유효 권한 | App 설치 권한 | **App 권한 ∩ 사용자 GitHub 권한** |
| 보관 | 사내 시크릿 관리 | 비밀 저장소 참조 (`token_ref`), 평문 DB 저장 금지. **Profile A에서는 `gh_identity_secret`의 AES-256-GCM 봉인이 그 자리를 대신한다** (CR-086 / `DEV-652`) |

수집용 App에 쓰기 권한을 부여하지 않는다. 사용자에게 없는 권한을 설치 권한으로 대체해 실행하지 않는다 (FR-GH-008 AC-4). 이 규칙이 깨지면 웹 UI가 GitHub 권한 모델을 우회하는 경로가 된다.

### 10.2 토큰 수명주기

```text
GitHub App 사용자 인가
      ↓
사용자 액세스 토큰 발급
      ↓
비밀 저장소에 저장 → DB에는 참조와 메타데이터만
      ↓
실행 직전 실체화
      ↓
gh 프로세스 환경 변수로 주입
      ↓
프로세스 종료와 함께 제거 (gh config에 영속 저장 안 함)
```

토큰이 나타나면 안 되는 곳: argv, URL, 질의 문자열, 애플리케이션 로그, 실행 이력, 감사 본문, 오류 메시지, 스트리밍 출력.

만료된 토큰의 갱신에 실패하면 재인가를 요구한다. 만료된 자격 증명으로 실행을 시도하지 않는다.

**Profile A의 봉인 — 비밀 저장소의 대체이지 동등물이 아니다 (CR-086 / `DEV-652`).** 단일 호스트에는 KMS도 시크릿 관리자도 없다. 그래서 「비밀 저장소에 저장」 단계를 이렇게 실현했다: 액세스·리프레시 토큰을 `.env`의 `GH_IDENTITY_VAULT_KEY`(64자 hex)로 AES-256-GCM 봉인해 `gh_identity_secret`에 넣고, AAD는 `user_id`다 — 다른 사용자의 행으로 옮겨 붙여도 풀리지 않는다. 봉인 해제는 실행기가 실행 직전에만 하고 결과는 프로세스 환경으로만 간다. **대가**: 호스트 전체가 탈취되면 `.env`의 키와 DB의 봉인이 함께 새어 토큰이 복원된다. DB 덤프·백업만으로는 복원되지 않는다(키가 없다). 사내가 KMS를 두면 `sealSecret`/`unsealSecret` 자리를 어댑터로 바꾼다 — 계약(`token_ref`)은 그대로다.

### 10.3 명령 주입 차단

| 위협 | 차단 방식 |
| --- | --- |
| 사용자 입력이 shell 메타문자로 해석 | shell을 경유하지 않는다. `spawn(고정경로, argv, { shell: false })` 등가 모델만 사용 |
| 명령 문자열 조립 | argv는 capability manifest와 타입이 있는 입력에서 조립한다. 문자열 연결 없음 |
| 임의 명령 실행기 | 제공하지 않는다. `gh alias --shell` 등가 기능도 `policy_blocked` |
| 확장을 통한 임의 실행 | 기본 차단. 관리자 허용 목록의 확장만 격리 환경에서 조건부 실행 |
| `gh api`를 통한 정책 우회 | command 경로와 동일한 신원·권한·위험도·감사 검사를 거친다. 인증 헤더 override 불가, 호스트 고정 |

### 10.4 비밀 값 입력 처리

`secret`, `variable`, `gpg-key`, `ssh-key`, `ruleset` 계열 명령은 비밀 값을 다룬다.

- 값은 stdin 또는 제한된 임시 파일로 전달한다. argv에 넣지 않는다.
- 임시 파일은 실행 workspace 안에 만들고 실행 종료와 함께 폐기한다.
- 입력한 비밀 값은 다시 표시하지 않는다. 이력에서도 재입력을 요구한다.
- 실행 미리보기의 argv에서 비밀 위치는 `<redacted>`로 표시한다.

### 10.6 운영 정책 결정의 경계 (CR-090)

운영자의 결정(운영 승인·철회, capability 차단·재개)은 **실행을 여는 결정**이다. 그래서 세 경계를 둔다.

- **DB 경계.** 결정은 `search-api`(`prs_app`)를 거쳐 들어오지만 `prs_app`에는 정책 표 쓰기 권한이 없다. 쓰기는 마이그레이션 030의 `gh_operations_policy_apply` 하나로만 가며, 그 함수는 `SECURITY DEFINER`(소유자 `prs_admin`)·고정 `search_path`(`pg_catalog, public, pg_temp`, 표는 스키마 한정)·`PUBLIC` 실행 회수·인자 모양 재확인을 갖는다. `search-api`·web에 `prs_admin` 자격을 배포하지 않는다 — 관리 연결은 여전히 `JOB-AUD-001` 전용이다. **이 경계가 막는 것은 애플리케이션 롤의 우회다.** 소유자(`prs_admin`)·superuser의 직접 변경은 경계 밖이며 그 계정은 운영 프로비저닝이 통제한다. 통합 시험이 `SET LOCAL ROLE prs_app`으로 직접 쓰기·스냅숏 활성화·실행 기록 revision 바꾸기·`running`이나 종료 상태로 새 실행 기록 바로 넣기(가드 PRS10)·같은 이름의 임시 표로 `search_path` 가로채기를 실제로 시도해 거절·무효를 본다. 함수 본문의 내장 함수·연산자는 스키마를 한정하지 않았다. 이것이 안전한 전제는 `prs_app`이 `public`에 객체를 만들 수 없다는 사실이다 — PostgreSQL 15부터 **새로 만든** 데이터베이스에는 `PUBLIC`의 `public` 스키마 CREATE 권한이 없고(업그레이드한 클러스터나 복원한 덤프는 기존 권한을 유지한다), 마이그레이션은 그 권한을 `prs_admin`에만 준다(019). 시험 DB의 카탈로그 시험이 이 불변을 걸고, 운영 DB는 런북 7.C 4단계에서 한 번 확인한다.
- **감사 원자성 (FR-AUTH-004 AC-6 예외).** 적용된 결정의 감사 한 행은 함수 안에서 변경과 **같은 트랜잭션**에 쓴다 — 감사를 남기지 못하면 결정도 커밋되지 않는다. 7.2절의 best-effort 규칙을 따르지 않는 유일한 자리다. 거절(역할·모양·충돌·부적격·키 재사용)은 상태를 바꾸지 않으므로 `recordAuditBestEffort`로 결과 코드를 남긴다. 액션은 본문 `action`에서 정하므로 `action`이 없거나 네 값이 아닌 요청은 남기지 않고(정본 어휘에 없는 액션을 만들지 않는다 — 아무것도 바꾸지 못한 시도의 흔적만 빠진다), 정책 잠금 대기 초과(503, 롤백돼 적용 없음)는 결정의 거절이 아니므로 남기지 않는다. 같은 트랜잭션이라는 결합 때문에 그 달의 `audit_record` 파티션이 없으면 정책 변경도 커밋되지 않는다(관측성 `RB-26`). `WP-075`의 원격 쓰기 감사(best-effort)는 GHE 쓰기가 DB 트랜잭션에 들어올 수 없어서 고른 규칙이라 여기로 복사하지 않았다. 감사 행에는 사유만 담고 비밀·실행 결과 원문을 담지 않는다. **이 시험은 `GATE-GH-06`(실제 GHE 쓰기 실행의 감사)의 증거가 아니다.**
- **요청 위조.** 변경 경로는 `application/json` 본문만 받는다 — 다른 사이트의 폼 POST(`application/x-www-form-urlencoded`·`text/plain`)는 400이고, JSON 본문의 교차 출처 요청은 사전 요청이 필요하다. 세션 쿠키는 `SameSite=Lax`다. 저장소 전체에 CSRF 토큰 체계는 없다(`THR-019`의 완화 문구와 다르다 — `DEV-691`).

위협은 10장 표의 `THR-048`~`THR-051`이다.

## 13. M 넘버 표기 쓰기 경로 보안 (CR-077 신규)

10장이 연 쓰기 경로는 **사용자가 지시한 실행**이었다. `CR-077`이 여는 것은 다르다 — `FR-SEQ-009`에 따라 M 넘버가 확정되면 시스템이 스스로 PR 제목을 갱신한다. 이 제품에서 **처음으로 사람의 지시 없이 발생하는 GHE 쓰기**이며, Search/Data Plane의 읽기 전용 원칙(2장 원칙 6)에 대한 두 번째 예외다. 이 장은 그 쓰기가 10장의 Operations Plane과 어떻게 다른지, 그 차이가 요구하는 통제가 무엇인지를 적는다.

### 13.1 세 번째 자격 증명 경계

10.1절은 Data App(조회, server-to-server)과 Operations App(사용자 지시 실행, user-to-server) 둘을 구분했다. M 넘버 표기는 그 둘 중 어디에도 속하지 않는 **세 번째 경계**다 — Data App처럼 server-to-server 설치 토큰을 쓰지만, Data App과 자격 증명을 공유하지 않는다(`FR-SEQ-009` AC-5).

| 항목 | Data App | M 넘버 표기 전용 App |
| --- | --- | --- |
| 인증 방식 | GitHub App 설치 토큰 (server-to-server) | GitHub App 설치 토큰 (server-to-server) — **별도 설치**, 별도 개인 키 |
| 권한 | 최소 read | `pull_requests:write`만 |
| 사용처 | 웹훅 보강, 백필, 권한 조회 | PR 제목 갱신(`JOB-SEQ-005`) 하나뿐 |
| 접근 주체 | `pipeline-worker`, `search-api` | `JOB-SEQ-005`를 실행하는 워커만. **`search-api`는 이 키를 읽지 않는다** |
| 보관 | 사내 시크릿 관리 (6장) | 사내 시크릿 관리 (6장) — Data App과 **다른 행**으로 별도 저장 |

**왜 공유하지 않는가.** 조회 자격 증명에 쓰기 권한을 얹으면, 그 토큰이 유출됐을 때의 피해 범위가 "읽기 전용 접근"에서 "PR 제목을 임의로 바꿀 수 있는 접근"으로 바뀐다. 읽기 전용이라는 사실 자체가 Data App 유출의 피해를 제한하는 통제였는데(THR-008), 쓰기 권한을 얹으면 그 통제가 사라진다. 분리하면 한쪽 자격 증명의 회전·폐기가 다른 쪽의 조회 가용성에 영향을 주지 않는다는 이점도 함께 따라온다.

### 13.2 감사

`pull_request.annotate` 액션이 추가된다(`FR-SEQ-009` AC-4). **정본은 `srs_final.md`의 `FR-AUTH-004` AC-1 감사 대상 액션 표이며, 7장의 원칙대로 이 문서는 여기서 다시 정의하거나 넓히지 않는다.** `target`은 `{repository}#{pr_number}`이고 `query`는 없다.

이 행은 정본 표에서 **행위자가 사람이 아닌 첫 행**이다 — 지금까지의 모든 감사 대상 액션은 사용자가 화면이나 API를 직접 눌러 만들었지만, `pull_request.annotate`는 `JOB-SEQ-005`가 스스로 기록한다. 7.2절의 실패 격리 규칙(감사 쓰기는 주 동작의 트랜잭션 밖에 있고, 그 실패가 주 동작의 결과를 바꾸지 않는다)은 행위자가 시스템 잡이어도 그대로 적용된다 — 표기 성공이 감사 실패로 되돌아가지 않으며, 감사 실패가 표기 재시도를 막지도 않는다.

**`result_code`의 어휘는 둘이다** (`CR-085`). **감사 로그를 읽는 사람이 이 목록 없이는 사유를 복원할 수 없으므로 이 문서가 소유한다** — `safe_marker.set`이 API 계약에서 같은 규율을 따른다.

| `result_code` | 무엇 | 언제 남는가 |
| --- | --- | --- |
| `annotated` | **이 잡이 제목을 바꿨다.** 요청을 보냈고 서버가 기대한 값을 돌려줬다 | `PATCH` 성공 뒤, 정본 표시 앞 |
| `annotated_observed` | **접두를 관측했으나 누가 썼는지 확정할 수 없다.** 앞선 시도가 응답을 받지 못해 `unknown`으로 남은 행을 다음 회차가 다시 보니 이미 접두가 있었다 | 결과 불명 행의 복구에서만 |

둘을 가르는 이유는 공식 API가 **응답을 받지 못한 요청의 적용 여부를 확인할 수단을 주지 않기 때문이다**(멱등성 키도, 요청 조회도 없다). 그 상황에서 접두를 보고 `annotated`를 남기면 「이 잡이 바꿨다」가 거짓일 수 있다 — 다른 주체가 같은 접두를 붙였을 가능성을 API가 가려 주지 않는다. **감사 건수가 「제목이 바뀐 횟수」를 말해야 하므로**, 확정된 것과 관측된 것을 다른 코드로 남기고 둘을 합산하지 않는다.

**쓰지 않은 회차는 아무것도 남기지 않는다.** 한 번도 시도하지 않은 행에서 이미 접두를 본 경우(멱등), 다른 M 접두라 덮지 않은 경우(`mismatch`), 정본이 바뀌어 멈춘 경우(`superseded`)가 그렇다. 남기면 감사 이력의 건수가 실제 쓰기 횟수를 말하지 않게 된다.

### 13.3 위협 모델

이 쓰기 경로가 여는 위협은 10장 표의 `THR-046`·`THR-047`이 정본이다(CR-077) — 이 절은 요약만 한다.

- **THR-046**: 잘못된 M 넘버가 PR 제목에 박히면 되돌리기 어렵다. 채번의 멱등·단조성과 표기의 불일치 기록(덮어쓰지 않음)이 1차 방어이고, 자동 되돌리기는 존재하지 않는다는 사실을 숨기지 않는다.
- **THR-047**: 표기용 쓰기 토큰이 조회 경로로 새면 안 된다. 13.1절의 자격 증명 분리가 그 완화다.

### 13.4 저장소별 해제

`FR-SEQ-009` AC-6에 따라 표기 대상 저장소는 설정으로 개별 해제할 수 있다. 해제된 저장소는 **채번(`FR-SEQ-008`)은 계속하되 표기(`FR-SEQ-009`)만 멈춘다** — M 넘버 자체는 조회 API(`API-SEQ-007`)로 여전히 얻을 수 있으므로, 표기를 끈다고 이 기능 전체가 사라지지 않는다. 이 스위치는 `THR-046`이 실제로 일어났을 때(잘못된 값이 계속 쓰이는 것을 막을 때) 가장 먼저 쓰는 대응이며, 저장소 단위이므로 문제가 확인된 저장소만 끄고 나머지 저장소의 표기는 계속된다.
